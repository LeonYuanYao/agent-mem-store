# MemStore Specification

Status: Accepted — Full Cutover is active; the post-Cutover reliability Architecture and Implementation Plan were approved and implemented in the repository working tree on 2026-08-26. Implementation Evidence Review is pending; live Runtime migration, installed-program replacement, Worker restart, and activation are not authorized.

## Purpose

MemStore will use the user's Obsidian-managed Memory Vault as durable, portable, and manually manageable long-term memory for Coding Agents such as Codex and Claude Code.

## Desired outcomes

- Important knowledge can be captured from Agent sessions with minimal interruption to the conversation.
- Agents can retrieve relevant long-term knowledge in later sessions.
- Scheduled governance can consolidate overlapping knowledge, identify or remove obsolete and invalid knowledge, and maintain useful relationships between knowledge items.
- The knowledge remains readable and manually manageable in Obsidian.
- The data can be backed up or migrated independently of the MemStore implementation.
- Repeated use should improve the usefulness of the store instead of causing unbounded, silent decay.

## Confirmed boundaries

- MemStore Project lives at `AgentScratchpad/MemStore` and contains program artifacts only.
- Memory Vault currently lives at `<vault-root>` and is the authority for personal memory data.
- Personal memory data does not enter the AgentScratchpad Git history by default.
- The project must not maintain a second authoritative copy of Memory Vault content.
- Machine-local vault discovery or configuration must be separable from portable project configuration.
- Machine-local Runtime Data defaults to `~/Library/Application Support/MemStore`. It is separate from the MemStore Project, Memory Vault, Agent-specific homes, temporary directories, and operating-system cache directories.
- The first-version primary runtime database defaults to `~/Library/Application Support/MemStore/state/memstore.sqlite`. It uses one main SQLite database with separate tables for operational domains; rebuildable large retrieval indexes remain outside the database.
- SQLite WAL and shared-memory files remain beside the main database while present. The live main database and its WAL state must never be placed in or synchronized through Memory Vault.
- The runtime root is configurable only through an explicit management operation. Hooks, Luna, scheduled governance, and automatic recovery cannot relocate it.
- The runtime root uses restrictive permissions by default and must reside on persistent storage. Runtime SQLite backup must use a consistent SQLite backup mechanism or a quiesced Worker rather than copying only a main database file while WAL state may exist.
- Memory Vault migration does not require Runtime Data after all pending work has completed, but omitting pending Outbox or governance work from a machine migration means that unfinished work will not follow automatically.
- The first-version portability contract is `complete long-term knowledge, not machine execution state`. Portable Canonical Memory Data includes Durable Memory bodies and revisions; authority, scope, applicability, validity, category, and user-control metadata; versioned Semantic Contracts and validated compact or standard representations; Project identities and display names without local paths; portable provenance identities; relationship and successor edges; retained Archived bodies; and permanent body-free Tombstones.
- Machine execution state does not migrate with an ordinary Vault move. This includes pending Outbox and Luna work, Governance cursors and leases, Injection Receipts, transient Bad Case diagnostics and Repair Bundles, Model Health Incidents, notification state, local Project root aliases, Sessions, logs, SQLite, FTS, embeddings, indexes, and caches.
- A first-version migration readiness check reports unfinished or uncommitted work and cannot call a Vault-only move complete while it remains. The ordinary supported flow drains required work, pauses capture and Workers, copies or synchronizes Memory Vault, validates Canonical Data on the destination, re-registers machine-local Project roots, rebuilds Runtime Data, verifies retrieval, and then enables destination capture.
- Existing Durable Memory remains meaningful without Luna regeneration. Exact metadata and FTS retrieval may become available before local embeddings finish; a complete semantic index is published atomically afterward. Local absolute paths are re-resolved and never define portable Project identity.
- Review Inbox is a generated view and is rebuilt from destination state. The first version neither merges two active Runtime databases nor supports two MemStore writers against one synchronized Vault. Source capture remains paused until destination validation and ownership handoff complete.
- A future explicit runtime export/import capability may migrate unfinished work through a versioned, consistent snapshot. It must quiesce the Worker or use the SQLite backup API, exclude rebuildable indexes by default, and revalidate machine paths and Project Registry mappings on import. It is an architecture allowance rather than a first-version implementation requirement.
- MemStore uses two non-overlapping, versioned TOML configuration documents. Portable knowledge behavior lives at `<Memory Vault>/_MemStore/policy.toml`; machine execution configuration lives at `~/Library/Application Support/MemStore/config.toml` by default.
- Portable policy includes knowledge lifecycle and retention, Project and Global policy, automatic injection budgets and reviewed thresholds, governance cadence and stable timezone, review cadence, and configurable Luna-health policy. Machine configuration includes Vault and Runtime paths, Agent adapter installation state, local embedding adapter and artifact location, Luna endpoint and credential reference, macOS notification and LaunchAgent state, and local Project root mappings.
- Passwords, tokens, API keys, cookies, and equivalent credentials cannot appear in either configuration. Machine configuration stores only an environment-variable or operating-system credential-store reference. The two schemas do not define overlapping keys or a hidden precedence chain.
- Both files support manual editing. A complete candidate configuration is schema- and cross-field-validated before atomic activation; invalid edits leave the last valid configuration active and produce a bounded diagnostic. Management commands use atomic replacement and retain one recoverable prior valid version.
- Compatible readers preserve unknown fields and warn rather than deleting them. A binary that encounters a higher unsupported schema version does not run write, governance, injection, or destructive work; it exposes bounded read-only status until a compatible version is used.
- Full Cutover and other explicitly reviewed high-risk actions are operations, not policy booleans. Editing either TOML file cannot silently perform them. Obsidian `.obsidian/` remains outside MemStore control.
- Obsidian's `.obsidian/` configuration is outside MemStore's write scope unless a later reviewed requirement explicitly adds it.

See [ADR-0001](./docs/adr/0001-separate-program-and-data.md) for the accepted program/data separation decision, [ADR-0031](./docs/adr/0031-place-runtime-data-under-macos-application-support.md) for the accepted machine-local runtime root, [ADR-0032](./docs/adr/0032-keep-live-sqlite-out-of-memory-vault.md) for the exact database path and migration boundary, [ADR-0083](./docs/adr/0083-migrate-long-term-knowledge-not-runtime-state.md) for the first-version portability contract, and [ADR-0084](./docs/adr/0084-separate-portable-policy-from-machine-configuration.md) for the two-file configuration boundary.

## Capture model

- Complete Agent sessions remain in the source Agent's native history system and are not copied into Memory Vault by default.
- MemStore distills potentially reusable knowledge from Source Sessions into Memory Candidates in the background.
- Each candidate retains provenance sufficient to identify its source Agent, session, time, and project.
- A candidate becomes a Durable Memory only after the validation or governance process authorizes it for normal recall.
- An unresolved hypothesis may be retained only as an explicitly unverified candidate; it must not be represented or recalled as an established fact.
- Importing a complete session into Memory Vault is a separate, explicit archival action.

See [ADR-0002](./docs/adr/0002-store-distilled-knowledge-not-transcripts.md) for the accepted distilled-knowledge capture boundary.

## Promotion policy

- Human-authored Memory has the highest content authority within its applicable scope and must not be silently overwritten by an automated process.
- Content explicitly supplied by the user in a Manual Memory Directive is a Direct Human Assertion and is treated as Human-authored Memory rather than Agent-derived content.
- A Direct Human Assertion's Canonical body is preserved without Luna semantic rewriting; only deterministic format normalization such as line endings or schema-safe metadata placement is allowed. Luna may propose separate derived metadata or validated retrieval representations. Any inferred, expanded, or materially reinterpreted statement becomes an Agent-derived Candidate rather than changing the Human-authored assertion or inheriting its authority.
- Knowledge extracted by Luna or another Agent from a turn, selected material, or a session remains Agent-derived and enters the Memory Candidate lifecycle even when the user explicitly authorizes its Project or Global scope. Scope authorization does not confirm the extracted content.
- An explicit update or replacement that identifies an existing Human-authored Memory authorizes a successor revision. The new assertion becomes active, while the previous memory is archived with provenance and a successor identity.
- A generic remember operation that conflicts with an existing Human-authored Memory does not imply replacement. The new assertion enters Human Conflict, remains outside normal recall, and requires an explicit choice to keep the existing memory, adopt the new memory, or distinguish their applicability.
- A direct Obsidian edit to the same Memory identity is an authoritative revision and does not require a second MemStore confirmation. Change detection retains revision provenance and rebuilds affected derived state.
- An Agent-derived candidate may be promoted automatically only when it is explicit, traceable, directly evidenced or successfully verified, clearly scoped, non-conflicting, and neither sensitive nor transient.
- Repetition is a supporting signal rather than a promotion prerequisite. A material fact, decision, constraint, preference, or lesson may qualify after one occurrence when its meaning and applicability are explicit and the available evidence satisfies the applicable gate.
- Luna splits mixed evidence into bounded atomic clauses and assigns each clause exactly one `retentionDecision`: `long_term`, `project_phase`, `session_only`, `no_memory`, or `uncertain`. Luna owns this semantic classification; deterministic MemStore code owns enforcement. Only `long_term` and `project_phase` clauses that are not task observations may enter the Memory Candidate lifecycle. `no_memory`, `session_only`, and task observations are rejected before Candidate creation, while `uncertain` is isolated without being relabeled as session-only or participating in normal recall.
- Distillation and consolidation may return at most 128 raw atomic clauses, but no more than 64 admitted clauses may enter Candidate creation. Exceeding the admitted limit is a visible retryable retention-validation failure rather than silent truncation. A non-empty Batch cannot complete with neither a Candidate nor a considered disposition. Consolidation cannot make an output retention decision less restrictive than the strictest cited input Candidate decision, and it cannot silently omit a durable input backed by an explicit user statement or by at least two distinct evidence-linked importance reasons without representing that input's evidence or an evidence-linked disposition.
- Shadow records every atomic Admission decision in a dedicated Machine-local Runtime Audit before enforcing the Candidate gate. This audit is excluded from the Memory Vault, Candidate queue, FTS, embeddings, relationships, retrieval, and injection. It retains a bounded model-derived statement and content hash only when a second local sensitivity check is Normal; otherwise both are absent. Audit rows expire after 14 calendar days and are pruned by a catch-up-aware daily maintenance cursor. Long-lived Batch and consolidation results contain admitted clauses only.
- Validation is selective and layered. Ordinary candidates with clear provenance and sufficient deterministic evidence take the lightweight path; they do not receive an additional Luna verification call merely for procedural uniformity.
- Lightweight promotion uses a reviewed evidence-class allowlist rather than a Luna confidence score. Eligible single-source evidence is limited to: an explicit and faithfully scoped user statement; a code or configuration fact bound to a file content identity and applicable repository revision; a captured command or test outcome with command, working directory, time, exit status, and intact bounded result; or an exact reference to existing Human-authored Memory that introduces no new inferred claim.
- A normal conversational user statement remains evidence for an Agent-derived extraction unless it was submitted through a Manual Memory Directive as a Direct Human Assertion. The lightweight path does not upgrade model-derived wording to Human-authored authority.
- An Agent summary without underlying evidence, truncated or integrity-ambiguous tool output, speculative language, a future plan, transient state, unclear applicability, a material conflict, or a conclusion synthesized across multiple observations is ineligible for lightweight promotion. It follows the full validation path or remains waiting.
- Numeric model confidence may be recorded for diagnostics, but it cannot make an evidence class eligible, satisfy an evidence requirement, or authorize promotion.
- High-value classification uses controlled semantic categories rather than a free-form importance score. Luna may propose `importance_tags`, a bounded reason, and evidence references; the deterministic Promotion Gate confirms eligibility, and an explicit user pin forces retention protection without confirming truth.
- Eligible high-value categories are: an explicit user decision, stable preference, constraint, or exception expected to affect later Sessions; an architecture invariant, API contract, security boundary, data-loss risk, or irreversible-operation requirement; a supported failure root cause, repair, recovery procedure, or recurrence hazard; expensive-to-rediscover environment, toolchain, build, deployment, or debugging knowledge; and a material limitation or applicability correction to an existing general rule.
- Routine activity and progress, temporary branch or task state, commands without a reusable conclusion, unverified future plans, duplicates with no new information, and Memory Echoes are not high-value by default.
- High-value status grants longer retention, stronger validation, and governance priority only. It cannot promote a candidate, increase content authority, replace evidence, or bypass scope, sensitivity, and conflict policy.
- High-value Candidates have no hard count or percentage quota. Queue pressure may delay bounded governance work but cannot delete or automatically demote a candidate solely because many candidates are classified high-value.
- High-value Inflation metrics include only Luna-auto-classified Agent-derived Candidates. Direct Human Assertions, explicit user pins, duplicates, Memory Echoes, retries, and candidates routed by deterministic Global or Human-conflict rules are excluded from the denominator.
- A Session-level provisional anomaly requires at least 12 eligible candidates in one Session and at least 10 high-value classifications.
- A Project rolling anomaly uses at least 50 eligible candidates from the current 30-day window and at least 100 eligible candidates from the preceding 90 days as baseline. It is provisional only when the current high-value rate is at least 60% and exceeds the baseline by at least 25 percentage points.
- Before a Project has 100 eligible historical candidates, it remains in cold start. A current window of at least 50 candidates with an 80% high-value rate may create a provisional anomaly but not a persistent conclusion by itself.
- A tag-dominance provisional anomaly requires at least 20 high-value candidates in the current window and one `importance_tag` on at least 80% of them.
- A provisional anomaly becomes persistent only after two consecutive non-overlapping windows or two consecutive Weekly Maintenance evaluations remain anomalous. Only persistent anomalies enter the governance digest and bad-case repair dataset; neither state changes candidate authority, truth, retention, or lifecycle automatically.
- These thresholds are versioned and configurable. Shadow Mode measures the real distribution and may propose adjustments, but neither Luna, metrics, scheduled governance, nor Shadow Mode may change the active thresholds without explicit human Review.
- Global candidates, material conflicts, cross-Batch or cross-Session consolidation, Review Suggestions affecting Human-authored Memory, and high-value candidates whose evidence is incomplete or semantically ambiguous require the full validation path.
- The full path first performs Deterministic Evidence Checks against existing source identity, repository revision, captured command results, provenance, schema, scope, sensitivity, and conflict state. Luna then performs Semantic Evidence Assessment only where support cannot be decided deterministically.
- Luna's assessment is structured, evidence-citing advice such as supported, partially supported, contradicted, or insufficient evidence. A local deterministic Promotion Gate owns the final lifecycle transition and cannot be bypassed by model confidence or wording.
- If the missing evidence would require running tests, builds, deployments, privileged commands, or high-risk external access, background governance creates a Verification Request instead of executing the action silently. Until sufficient evidence arrives, the candidate waits outside normal recall.
- Inferred preferences, unresolved hypotheses, conflicting claims, fast-changing state, and conclusions without applicability conditions remain candidates outside normal recall.
- Clearly incorrect or prohibited content is rejected rather than retained by default.

See [ADR-0003](./docs/adr/0003-use-tiered-memory-promotion.md) for the accepted tiered-promotion authority model, [ADR-0016](./docs/adr/0016-distinguish-direct-human-assertions-from-model-extractions.md) for the accepted direct-assertion boundary, [ADR-0017](./docs/adr/0017-require-explicit-resolution-for-human-authority-conflicts.md) for same-authority conflict handling, [ADR-0025](./docs/adr/0025-use-selective-layered-candidate-validation.md) for the accepted evidence-assessment and final-gate boundary, [ADR-0029](./docs/adr/0029-classify-high-value-candidates-with-controlled-tags.md) for the accepted high-value classification boundary, and [ADR-0030](./docs/adr/0030-detect-high-value-inflation-with-conservative-baselines.md) for anomaly detection and threshold ownership.

## Sensitive information

- MemStore classifies captured and manually edited content as Secret, Private, or Normal and applies the highest detected sensitivity throughout capture, distillation, storage, retrieval, and governance.
- Luna may classify sanitized content as Private or Normal but cannot downgrade a local Secret classification. Users may raise sensitivity; lowering Secret requires an explicit False-positive Secret Override and cannot be used to admit actual credentials.
- Secret Content includes credentials and equivalent authentication material such as passwords, API tokens, private keys, session cookies, and authorization headers.
- The first-version local detector directly classifies high-confidence structured credentials such as PEM private keys, authorization or bearer headers, session cookies, provider token formats with stable structure, service-account private-key fields, and non-empty values bound to credential field names in supported text or structured data.
- Generic high-entropy text is not sufficient by itself to classify Secret. Entropy combined with authentication or credential context but without enough evidence for high-confidence classification enters the accepted body-free Sensitivity Quarantine. Known benign forms such as hashes, UUIDs, commit identities, public keys, file paths, and explicit test placeholders require negative regression coverage to control false positives.
- High-confidence Secret patterns are detected locally before durable capture where possible. Their bodies are redacted from Durable Outbox payloads and never sent to Luna, written to Memory Vault, indexed, injected, logged, archived, or retained in Memory Tombstones.
- Only a non-reversible keyed fingerprint, category, and timestamps may be retained to prevent repeated extraction and diagnose rejection.
- Private Memory may be stored and governed within Project scope but cannot be promoted automatically to Global Memory.
- A Global Private memory requires an explicit human directive and remains classified as Private for retrieval enforcement.
- Normal Memory follows the standard Project and Global policies.
- Human-authored Obsidian content that appears to contain a Secret is not automatically rewritten or deleted. It is excluded from indexes and Memory Injection and produces a bounded warning.
- Uncertain sensitivity enters a local Sensitivity Quarantine without normal recall or Luna processing.
- Sensitivity Quarantine is a body-free eligibility and audit state, not a second store for suspected Secret content. MemStore persists only a Quarantine identity, Project, Session or Turn identities where available, source kind and safe locator, non-reversible fingerprint, detector rule and version, risk category, reason, timestamps, source availability, and lifecycle state. It does not retain the suspected value or a reversible excerpt. New ephemeral observations retain the bounded `agent:event_kind` source kind needed for aggregate detector assessment; preexisting observations with no truthful source metadata remain `legacy_unknown`.
- When an original source such as a Vault or ordinary file remains readable, the Quarantine record binds its safe locator and content identity so a later local detector version or explicit review can re-read the current source in place. MemStore does not copy the suspect body. If an ephemeral Prompt, Tool output, or unstable transcript cannot be re-read, the body is intentionally lost; a false-positive decision then requires explicit resubmission of safe content.
- Quarantine outcomes are `confirmed_secret`, `false_positive`, `sanitized_replacement`, or `discarded`. Confirmed Secret retains at most a body-free rejection fingerprint or tombstone; false positive uses the exact override contract and reprocesses only a still-readable matching revision; sanitized replacement creates a new independently screened Candidate; discarded removes diagnostic metadata according to retention policy.
- Background Quarantines are aggregated into the Review Inbox and body-free notification policy rather than interrupting each turn. Inbox rendering is bounded by risk-category/source-kind groups, not Finding count: it reports exact aggregate counts and time ranges plus at most three recent Finding identities per group. Retained body-free metadata remains Machine-local Runtime Data and is available through `sensitivity status` and exact `sensitivity inspect`; it is not copied into the Vault view. A user-initiated manual remember operation immediately returns its Quarantine identity, risk category, no-body-retained status, and available review or safe-resubmission action.
- Ordinary body-free `blocked_secret` and `quarantined` Finding metadata defaults to 15 calendar days from `last_seen_at`. A new independently persisted occurrence refreshes that time. The Worker prunes expired observation rows and Findings in bounded local batches every six hours, catches up after downtime, and never calls a model for this decision. If work remains it continues after 30 seconds; transient failure uses bounded exponential retry and becomes a Review Inbox incident only after three consecutive failures. Deletion creates no Tombstone: a later recurrence is screened normally and creates a new Finding identity. Active exact-revision safety overrides and their invalidated audit records retain the separate protection and lifecycle defined below.
- A detector-rule change may locally rescan a still-readable unchanged source. It cannot infer safety from old metadata, send the suspect body to Luna, or recover an unavailable body. Luna, governance, and metrics cannot approve a false-positive override.
- A False-positive Secret Override is an explicit user action bound to the non-reversible content fingerprint, detector rule identity and version, and current content revision. It is not a global or pattern-wide detector disable.
- A relevant content change or material detector-rule change invalidates the override and triggers local re-evaluation before Luna, indexing, or injection becomes eligible again.
- Override applies to one exact detection rather than a whole note, field name, detector family, or pattern. Every other finding in the same content remains independently blocked or quarantined.
- Approval first re-reads the original source and verifies the same content revision locally. If the source is unavailable because it was ephemeral or removed, MemStore cannot approve from body-free metadata; the user must explicitly resubmit safe or sanitized content.
- Override audit data is machine-local Runtime Data. It contains the override, finding, and operation identities; Project; safe source locator; source content identity; keyed suspect fingerprint; risk category; detector rule identity and compatibility version; decision and controlled reason category; timestamp; human operation provenance; and later invalidation state. It never contains the suspected value or surrounding excerpt.
- An active exact-revision override has no arbitrary time expiry. After it is invalidated or its source disappears, the body-free audit record defaults to 180 calendar days before deletion. Migration to another machine does not silently transfer an active safety exception; the destination safely re-evaluates and may require another explicit decision.
- The first version has no force-store path for content that the user confirms is a real password, API token, private key, session cookie, authorization header, or equivalent credential. Such content remains prohibited from MemStore persistence and disclosure paths.
- A valid false-positive override for a manually authored Obsidian note restores eligibility for ordinary classification, indexing, and injection without modifying the note body. A true Secret manually present in the Vault remains excluded and warned about rather than silently rewritten or deleted.
- Override and warning surfaces identify the affected file or Memory identity, safe source locator, risk category, detector reason, source availability, and next actions without displaying the suspected Secret value. MemStore reports a suspected Secret; it never tells the user that its own decision is known to be wrong.
- The primary user action is labeled `I confirm this is not a password or credential; allow only this version`, not the implementation term `False-positive Secret Override`. It is accompanied by a warning to use sanitized resubmission when uncertain. Other actions are confirm Secret, submit sanitized replacement, and discard.
- Manual remember reports the block or quarantine and Review identity immediately. Background findings remain non-interrupting, enter the Review Inbox as Sensitivity Quarantine Aggregates, and use the accepted aggregate notification flow. A source-backed item links to the original local source for human inspection; a body-free ephemeral finding exposes no approve action. Aggregate concentration can motivate detector tests or safe resubmission, but cannot approve an individual or category-wide false-positive override.
- Before Full Cutover, synthetic credentials and representative non-Secret negative samples must prove classification, quarantine, exact false-positive override, revision invalidation, and absence of original Secret values from Outbox, SQLite, Vault-derived files, indexes, embeddings, Injection Receipts, logs, Review Inbox, and notifications.

See [ADR-0013](./docs/adr/0013-classify-and-contain-sensitive-memory.md) for the accepted sensitivity and containment boundary, [ADR-0020](./docs/adr/0020-restrict-secret-overrides-to-false-positives.md) for the accepted override boundary, [ADR-0068](./docs/adr/0068-quarantine-suspected-secrets-without-retaining-bodies.md) for uncertain-content handling, [ADR-0069](./docs/adr/0069-block-structured-secrets-and-quarantine-contextual-uncertainty.md) for the MVP detector rule boundary, [ADR-0081](./docs/adr/0081-explain-and-approve-only-an-exact-secret-finding.md) for the user-facing review and exact-finding audit contract, and [ADR-0113](./docs/adr/0113-aggregate-sensitivity-quarantine-for-human-review.md) for the accepted Ledger/Inbox aggregation boundary.

## Encryption boundary

- The first MemStore version does not implement application-level, field-level, note-level, or Vault-wide encryption.
- Canonical Memory Data remains human-readable Markdown so Obsidian viewing, manual editing, backup, and migration do not require MemStore keys or a decryption runtime.
- The first version does not introduce key generation, key storage, recovery phrases, automatic decryption, or encrypted-note formats.
- Private Memory is plaintext within the user's Vault protection boundary. Secret Content remains prohibited from persistence; lack of encryption does not permit credential storage.
- Machine-local Durable Outbox, Governance Ledger, indexes, caches, and logs use restrictive filesystem permissions and Secret redaction.
- MemStore does not claim that filesystem permissions, FileVault, storage-provider encryption, or Obsidian Sync encryption are application-level encryption that it provides or controls.
- Future encryption requires a separate reviewed ADR covering threat model, key recovery, Obsidian usability, sync and backup, schema migration and rollback, encrypted retrieval, and failure recovery.

See [ADR-0014](./docs/adr/0014-defer-application-level-encryption.md) for the accepted first-version encryption boundary.

## Candidate lifecycle

- Memory Candidates live in a Governance Queue and do not participate in normal recall.
- Automated governance screens candidates for prohibited content, compares them with existing knowledge, validates available evidence, and selects one of six outcomes: promote, merge, wait, conflict, reject, or expire.
- The Promotion Gate, not Luna, selects and commits the lifecycle outcome. Luna provides Semantic Evidence Assessment only for candidates routed to the full validation path.
- A failed or unavailable Luna assessment leaves full-path work retryable or waiting; it cannot be interpreted as approval. Lightweight deterministic work that does not depend on Luna may continue independently.
- Verification Requests are durable, non-promoting governance work. Completion adds new provenance-bound evidence and causes re-evaluation rather than directly forcing promotion.
- New related evidence and scheduled governance runs may re-evaluate waiting candidates.
- A conflict cannot silently overwrite a Durable Memory or Human-authored Memory.
- Rejected content may leave a minimal rejection record, such as a fingerprint, reason, and timestamp, to prevent repeated extraction without retaining the rejected body indefinitely.
- Ordinary waiting candidates default to a configurable 90-calendar-day retention period measured from `last_evidence_at`.
- A candidate classified as high-value, linked to an unresolved Verification Request, or held by a material conflict defaults to a configurable 180-calendar-day retention period measured from `last_evidence_at`.
- User-pinned candidates do not expire automatically.
- Only materially new, valid, provenance-bound evidence advances `last_evidence_at`. Processing retries, repeated extraction of the same support, Memory Echoes, reads, ranking outcomes, and governance no-ops do not extend retention.
- Reaching the retention deadline creates an expiration obligation; it does not directly delete or expire the candidate. A successful governance evaluation must recheck state, evidence, protection, and conflicts before committing `expired`.
- A candidate that has not received a required successful processing opportunity because Luna, the network, the Worker, the Vault, or its governance backlog was unavailable cannot expire for that reason. Catch-up processing evaluates it after recovery without interpreting downtime as negative evidence.
- Committing `expired` removes the candidate body instead of creating another body-bearing candidate archive. The removal occurs only after the successful expiration evaluation and its durable state transition have been recorded.
- Expiration creates a body-free Candidate Tombstone containing only the candidate fingerprint, Project and scope identifiers, source identities, expiration reason, and timestamps needed for deduplication and audit. It must not retain the claim, evidence text, prompts, tool output, or Secret Content.
- Candidate Tombstones default to a configurable 180-calendar-day retention period. An exact repeat with no materially new independent evidence is deduplicated during that period; materially new evidence may create a new candidate linked to the tombstone and is not permanently suppressed.
- Candidate Tombstones are deleted after their retention period unless explicitly pinned or still referenced by an active governance object. References cannot be manufactured by retries, duplicate extraction, or Memory Echoes merely to prevent cleanup.

Human Conflict is not an Agent-derived Memory Candidate and does not enter normal automatic promotion. It retains the user's new assertion durably outside normal recall until an explicit resolution records whether the existing memory remains active, the new assertion becomes its successor, or both are retained with non-conflicting applicability conditions.

See [ADR-0026](./docs/adr/0026-retain-waiting-candidates-by-evidence-age.md) for the accepted candidate-retention clock, defaults, and failure-recovery boundary and [ADR-0027](./docs/adr/0027-remove-expired-candidate-bodies-and-retain-temporary-tombstones.md) for post-expiration cleanup.

## Bad-case diagnostics and manual repair

- Bad Cases are machine-local diagnostic objects, not Canonical Memory Data or Durable Memory. They remain under `~/Library/Application Support/MemStore` and do not enter Memory Vault.
- `state/memstore.sqlite` owns each Bad Case identity, kind, Project, severity, lifecycle state, timestamps, reminder state, linked object identities, diagnostic-bundle path, and checksum.
- A readable diagnostic bundle is stored as `badcases/bc_<id>.json`. It contains bounded, Secret-screened context required for later diagnosis: Agent, Session, Turn, and Project identities; relevant Injection Receipt, Candidate, Memory, and revision identities; selected or omitted item identities and score components; filter and threshold decisions; relevant index, ranking, Prompt, model, configuration, and code versions; explicit observed labels such as `irrelevant`; aggregate anomaly measurements; bounded sanitized excerpts where safe; and source-availability status.
- A Bad Case bundle does not contain a complete Session, full tool inputs or outputs, unscreened prompts, Secret Content, a full Memory Vault body, or a model-invented statement of what the user supposedly expected.
- SQLite owns lifecycle state while JSON owns the readable diagnostic payload; paths and checksums bind them without making either a second knowledge authority.
- `repair-bundles/repair_<id>/` is created only when the user explicitly starts the repair Skill. It may contain `diagnosis.md`, `proposed-changes.md`, `reproduction.json`, and `verification-plan.md` for a user-started Codex + GPT-5.6 repair workflow.
- A Repair Bundle does not authorize silent changes. Prompt, threshold, retrieval, code, configuration, or knowledge-data changes still follow explicit review gates and fresh verification.
- Bad Case detection and reporting can run automatically; product repair cannot. The repair Skill explains context, objectives, constraints, and expected evidence to the foreground repair Agent.
- Repeated occurrences with the same normalized Bad Case Signature aggregate into one Bad Case instead of creating one JSON file per occurrence. The signature uses failure kind, affected component, Project or scope, and relevant version dimensions without storing raw Prompt or Secret content.
- Each aggregate records `first_seen_at`, `last_seen_at`, total occurrence count, affected versions, and at most 20 body-bearing representative samples. The bounded set preserves the earliest, recent, and deterministically selected diverse examples; additional occurrences contribute lightweight counts and measurements only.
- Only a new, independently observed failure occurrence advances `last_seen_at`. Scans, retries, reminders, reprocessing, and duplicate import do not extend retention.
- An `open` Bad Case diagnostic body defaults to 180 calendar days from `last_seen_at`. If no recurrence or human repair activity occurs, it becomes `stale`, its diagnostic body is removed, and a body-free summary remains for another 180 calendar days. `stale` means not recently reproduced, not verified as fixed.
- After `resolved` or `dismissed`, diagnostic bodies and completed or abandoned Repair Bundle bodies remain for 30 calendar days, then are removed. A body-free repair and regression Ledger remains for 180 calendar days from closure.
- A matching occurrence during the body-free Ledger period opens a linked regression case and captures fresh diagnostics rather than restoring deleted bodies or assuming the old fix still applies.
- An active repair retains the required Repair Bundle. Explicitly pinned Bad Cases or Repair Bundles do not expire automatically. Cleanup rechecks active references and cannot run early because a Worker, model, or governance backlog was unavailable.
- The foreground repair Skill is named `$memstore-repair`. It accepts one or more Bad Case identities or an aggregate signature and loads the corresponding diagnostic bundles, lifecycle state, and current MemStore code and configuration versions.
- The Skill requires a user-started Codex + GPT-5.6 repair Session. It cannot switch the active model itself; if model identity cannot be confirmed, it warns rather than claiming the requirement is satisfied.
- Repair begins read-only. It identifies whether evidence points to extraction Prompt, importance classification, retrieval ranking, thresholds, instrumentation, source-data quality, or knowledge content. A failure that cannot be reproduced becomes `not_reproduced` with explicit missing evidence, not `resolved`.
- Review Gate 1 presents the evidence-backed root cause, proposed files and behaviors to change, expected impact, risks, rollback method, and verification plan. No repair edit occurs before explicit approval.
- After approval, edits are limited to the authorized MemStore Project code, Prompt, configuration templates, and tests. A required Memory Vault content change becomes a separate explicit Memory operation rather than an incidental repair edit.
- Repository regression fixtures derived from real cases are minimal, sanitized, and synthetic. Raw local diagnostics do not enter Git-tracked fixtures.
- The repair runs targeted tests, Bad Case offline replay, and any required Shadow comparison and reports both improvement and newly introduced harm before Review Gate 2.
- Review Gate 2 authorizes activation of changed Prompt, ranking, threshold, or runtime configuration and the Bad Case lifecycle decision. The Skill does not automatically commit, push, install global Hooks, restart active components, modify Codex global configuration, or mark a case resolved.
- A deterministic implementation or instrumentation repair (class A) may become `resolved` at Review Gate 2 without an additional runtime observation period when a pre-fix regression test reproduces the failure, the post-fix test and affected suite pass, the original Bad Case replay passes, and no known regression is introduced.
- A Prompt, retrieval-ranking, or threshold repair (class B) may become `resolved` at Review Gate 2 without an additional runtime observation period when the pre-fix Bad Cases and protected regression set were frozen, all explicitly reported cases pass, aggregate representative targets are met, irrelevant injection and critical recall do not regress, no scope, authority, sensitivity, or conflict boundary regression appears, and evaluation labels and gates were not weakened during repair.
- An authority, scope, Secret, Human-authored, or equivalent safety-boundary repair (class C) enters `monitoring` after its tests pass and Review Gate 2 authorizes controlled activation. It requires at least seven consecutive calendar days and at least 30 Relevant Safety Opportunities with zero known boundary violations before becoming `resolved`.
- Any class C violation fails the current monitoring cycle; a new repair starts a new observation period. If 30 opportunities have not occurred after seven days, observation continues automatically for at most 14 days total.
- At 14 days with fewer than 30 opportunities, MemStore does not auto-resolve. The user chooses continued monitoring or `resolved_with_limited_evidence`; the latter records the opportunity count, missing coverage, decision provenance, residual risk, and rollback version.
- Class C monitoring retains the prior version and a verified rollback path. Ordinary Sessions, unrelated Turns, and duplicate replay do not count as Relevant Safety Opportunities.

See [ADR-0033](./docs/adr/0033-store-bad-case-state-and-diagnostics-separately.md) for the accepted Bad Case and Repair Bundle storage boundary, [ADR-0034](./docs/adr/0034-aggregate-and-bound-bad-case-diagnostics.md) for occurrence aggregation and retention, [ADR-0035](./docs/adr/0035-repair-bad-cases-through-a-reviewed-foreground-skill.md) for the accepted repair workflow and authority boundary, and [ADR-0036](./docs/adr/0036-resolve-repairs-by-risk-tier.md) for the accepted resolution evidence.

## Active Memory capacity

- A Memory Space is either one Project identity or the separate Global scope. All registered roots that resolve to the same Project identity share one Project capacity; directory count does not multiply the allowance.
- Capacity has two layers: the complete durable corpus and a bounded automatic-ranking working set. Only Agent-derived Active Durable Memory in that working set counts toward managed foreground capacity. Human-authored Memory remains authoritative and exempt.
- Project defaults are a high water of 2,500, a hard limit of 3,500, and a low water of 2,200. Global defaults are 300, 500, and 270. The recent-activity window is seven days. These values are reviewed portable policy, never adaptive model output.
- Above high water, deterministic local reconciliation keeps hard-protected and recently active entries, then fills to low water by descending last activity, deterministic soft-signal tie-breakers, and Memory identity. It records reversible machine-local ranking exclusions; it does not revise, archive, delete, or relocate canonical Markdown.
- Hard protection is limited to explicit pin or retain-forever, `startup: always`, open conflict/verification/review work, and the controlled `safety_data_integrity`, `failure_recovery_hazard`, and `preference_constraint` categories. Model-derived importance, high-value, evidence count, relationships, priority, and generic preserved-negation metadata are soft ranking signals only.
- SessionStart and UserPromptSubmit use the bounded working set. Explicit MCP, Skill, search, identity, related, and provenance reads continue over the complete Active durable corpus and do not use automatic cold rescue. An explicit selected read reactivates an excluded revision for the next foreground snapshot.
- Working-set publication reuses the current retrieval documents and vectors. It neither invokes Luna/Terra nor rebuilds embeddings, and it does not change automatic injection token budgets.
- Crossing high water creates a recoverable local obligation. The Worker catches missed wake-ups and resolves pressure no later than six hours after observation when local storage is available. Snapshot-publication failure retains the prior larger foreground set and retries without losing knowledge.
- At the hard limit, ordinary Agent-derived Candidate promotion waits with reason `memory_space_capacity_hard_limit`; the limit is evaluated against ranked Agent-derived Memory plus in-flight reservations, not the complete durable corpus. Capture, distillation, Candidate retention, Human-authored writes, and explicit retrieval continue.
- If hard-protected entries exceed low water, reconciliation retains them and exposes `low_water_unreachable`; it never weakens protection to satisfy a numeric target. Successful routine rebalancing does not create per-Memory Review Inbox noise.
- Durable-corpus reduction remains separate. A Memory may leave the corpus only through reviewed successor/correction/invalidation, source-first transient cleanup, explicit user action, or future atom-preserving consolidation. Age or low retrieval frequency alone is insufficient.
- Runtime metrics, models, and scheduled governance cannot silently change thresholds, weaken protection, enable automatic cold rescue, or convert a ranking exclusion into archival or deletion.

See [ADR-0121](./docs/adr/0121-bound-active-agent-memory-per-space.md) for the accepted capacity, protection, and recovery boundary.

## Archive and purge

- Obsolete Durable Memory is archived before it is physically purged.
- Archiving immediately removes the memory from normal recall and relationship expansion while preserving it for recovery during its effective retention period.
- An archive event records `archived_at`. Retries, repeated governance, file moves, and no-op updates do not reset it; an explicit restore followed by a later archive starts a new cycle.
- Retention precedence is an explicit per-memory `purge_after` or `retain_forever` directive, then an authority- or scope-specific policy, then the system default.
- Archived Memory defaults to three calendar months before purge, regardless of whether its authority is Agent-derived or Human-authored. This duration is configurable rather than hard-coded; Human-authored content still cannot be archived automatically by an Agent.
- Three months means three calendar months from the immutable `archived_at`, not an approximate elapsed-day duration. At archive time, the resolved policy is materialized as a fixed `purge_after` on that archive cycle. The accepted three-month transition explicitly backfills existing unprotected archives from their original `archived_at`; later policy changes apply prospectively unless another governed bulk transition is approved.
- User-pinned content remains protected unless an explicit purge directive overrides it.
- An expired retention period creates an idempotent purge obligation in the Governance Ledger. Offline or failed runs catch up later under bounded deletion batches.
- The Worker checks no less often than every six hours, retries failures with bounded backoff, and uses a machine-local managed staging copy outside both Vault and Runtime. Staging survives interrupted deletion and is removed after the corresponding purge backlog completes.
- Before purge, the worker rechecks that the memory remains archived, has not been restored or protected, and matches the expected content identity.
- Purge has one machine-local executor and processes each Memory through checkpointed prepare, body removal, Tombstone commit, derived-index removal, and completion states. Recovery rechecks current lifecycle and content identity before continuing any incomplete state; a batch is not one unbounded cross-file transaction.
- The first-version configurable purge batch stops after 25 Memory bodies, 16 MiB of removed body data, or ten seconds of destructive work, whichever occurs first. It checks for foreground Hook, capture, or indexing pressure before each item and yields without losing its checkpoint.
- When more eligible work remains and foreground queues are clear, the next batch may start after a 30-second floor. If purge yielded to foreground pressure, it waits at least five minutes before retry. Only ordinary bounded incremental SQLite reclamation is allowed; a purge batch never performs a full `VACUUM` automatically.
- Batch item, byte, and time ceilings may be lowered through portable policy. Raising them above the initial safety maxima of 200 items, 128 MiB, or 60 seconds requires an explicitly reviewed configuration change rather than Luna or adaptive governance. Preview enumerates the bounded next batch without deleting or reserving it.
- Purge removes the archived body and retains a minimal body-free Canonical Memory Tombstone by default. It includes only Memory and revision identities, Project or Global scope, authority, content identity, `archived_at`, `purged_at`, purge reason, successor identity, and body-free provenance identities as applicable. It contains no body, compact or standard representation, embedding, source excerpt, or recoverable content and is excluded from ordinary recall, semantic indexing, and relationship expansion.
- Tombstones have no automatic time-based expiry in the first version. They preserve replay suppression, idempotency, old-reference explanation, successor continuity, deduplication, and portable migration history without retaining knowledge content.
- A future explicit Tombstone compaction or prune may be added only after a separate Review defines a provable replay watermark and verifies that no Durable Memory edge, pending Outbox or governance work, Verification Request, Bad Case, Retrieval Receipt, backup-import contract, or migration artifact can still depend on the record. Time elapsed alone is not sufficient authority to delete it.
- Restore before body purge resumes the archived content under the accepted lifecycle. After body purge, Tombstone data alone cannot restore content; reconstruction from a surviving external source creates a provenance-bound new revision instead of pretending the deleted body was recovered.
- The explicit `archive` and `restore` command surfaces accept one portable or Canonical Memory identity, preview by default, and require `--apply` to write a new Canonical revision. They preserve body and authority. Restore clears the completed archive cycle's timestamps and purge deadline so a later archive receives a fresh deadline.
- `purge-memory` is a CLI-only high-risk single-Memory surface. It accepts Archived Memory only, refuses pin, `retain_forever`, and open review, verification, or conflict protections, requires a separately verified Vault backup, and requires an approval digest bound to the exact previewed body, revision set, and backup. It may bypass the ordinary retention deadline only through that explicit per-Memory user approval. No generic `forget` alias or MCP physical-deletion tool is exposed.
- Prohibited sensitive content may bypass normal retention only under a separately reviewed safety policy. External backups and Obsidian Sync history are outside MemStore's deletion guarantee.

See [ADR-0012](./docs/adr/0012-archive-before-purge-with-configurable-retention.md) for the accepted archive, configurable retention, and purge boundary, [ADR-0079](./docs/adr/0079-retain-body-free-tombstones-without-time-expiry.md) for fixed archive-cycle deadlines and Tombstone retention, [ADR-0085](./docs/adr/0085-purge-in-small-checkpointed-yielding-batches.md) for the destructive-work budget, and [ADR-0129](./docs/adr/0129-expose-preview-first-memory-lifecycle-controls.md) for explicit single-Memory controls.

## Scheduled governance and recovery

- Continuous processing screens new candidates, handles retries, and detects direct conflicts.
- Daily maintenance performs incremental deduplication, expiration evaluation, relationship completion, and Retrieval Index health checks.
- Weekly Luna maintenance deeply consolidates overlapping knowledge, reviews relationships and staleness, and may produce an optional governance summary.
- A Human Memory Review Digest is generated on a configurable cadence, weekly by default, and is delivered only when unresolved Human Conflict or Review Suggestion items exist.
- Monthly maintenance audits overall knowledge health and recoverability without performing unbounded automatic deletion.
- A clock or operating-system scheduler is only a wake-up mechanism. A durable Governance Ledger is the authority for pending maintenance obligations.
- The ledger records each job's schedule, last successful cursor, attempts, lease, checkpoint, next retry, and failure state.
- Worker startup, machine wake, new capture activity, and explicit maintenance commands reconcile overdue jobs.
- Shutdown, sleep, lost wake-ups, network outages, model unavailability, worker crashes, and temporarily unavailable Vault writes must not silently skip a required maintenance cycle.
- Execution is at-least-once with idempotent effects. A job is successful only after its required durable results and cursor are committed; expired leases and partial checkpoints are recoverable.
- Network-dependent Luna work remains pending and retries with bounded exponential backoff and jitter. Independently valid local work may continue without marking the complete job successful.
- Missed calendar occurrences are coalesced into one Catch-up Run over all data since the last successful cursor instead of replaying every missed tick.
- Recovery order is continuous and daily work before weekly consolidation, then monthly audit. Catch-up concurrency and work budgets must protect foreground capture and injection.
- Backlog age, last success, retry state, and aggregated failure reasons are observable through commands and low-frequency health summaries without creating a mandatory approval inbox.

See [ADR-0011](./docs/adr/0011-make-governance-schedules-catch-up-and-recoverable.md) for the accepted governance cadence and missed-run recovery policy.

## Governance authority

- Luna may automatically merge, supersede, or archive Agent-derived Durable Memory only when newer or stronger traceable evidence supports the change, applicability conditions and scope are preserved, and no Human-authored Memory conflict exists.
- Capacity pressure is one narrow additional archival authority for Agent-derived Memory only. It requires the accepted coldness and protection checks, local revalidation, a durable Capacity Governance Obligation, and ordinary recoverable archive retention; it grants no authority over Human-authored Memory and no direct deletion authority.
- Every automatic semantic governance action is idempotent, recorded in the Governance Ledger, and recoverable. Superseded or archived bodies follow the accepted archive and retention policy instead of being silently overwritten or immediately deleted.
- Luna cannot automatically rewrite, merge, or archive Human-authored Memory merely because the model judges it stale, conflicting, redundant, or less useful.
- Suspected problems in Human-authored Memory produce a Review Suggestion with reason and evidence references. The original memory remains active; when it is relevant to retrieval, the injected representation includes a bounded warning rather than silently hiding it or making it effectively undiscoverable.
- A Review Suggestion is Agent-derived governance metadata and cannot inherit Human-authored authority or change the user's original statement.
- Deterministic automation may execute explicit human-authored directives such as `valid_until`, a targeted replacement, `purge_after`, or `retain_forever`. Its authority comes from the directive, not from Luna's judgment.
- Independent safety containment remains enforceable. In particular, detected Secret Content is excluded from Luna, indexes, and injection as defined by ADR-0013, but MemStore does not silently rewrite or delete the user's Obsidian source text.

See [ADR-0018](./docs/adr/0018-limit-automatic-governance-by-content-authority.md) for the accepted automatic-governance authority boundary.

## Human review reminders

- MemStore aggregates unresolved Human Conflict and Review Suggestion items into a low-frequency Human Memory Review Digest rather than notifying once per item.
- The default cadence is weekly and configurable. An empty review set produces no notification; unresolved items are subject to a reminder cooldown and may be snoozed without being resolved.
- The first-version primary reminder adapter is a native macOS Notification Center notification containing only aggregate counts and issue categories. It does not include memory bodies, evidence text, credentials, or other sensitive content.
- The notification is emitted by a minimal MemStore-owned macOS Notifier, not by Obsidian. It remains able to notify while Obsidian is closed, does not call Luna, and does not read or display candidate or memory bodies.
- The primary actions are to open the Review Inbox in Obsidian or snooze the reminder. The default generated view is `_MemStore/Review Inbox.md` in Memory Vault and is opened through an encoded `obsidian://open` URI.
- Obsidian is the detailed review surface rather than the notification runtime. The first version does not develop or install an Obsidian notification Plugin and does not modify `.obsidian/` for reminder delivery.
- Review Inbox is a rebuildable governance view, not Canonical Memory Data. It links to source memories and presents issue type, reason, evidence references, last-confirmed time, affected Projects, and available resolution operations without copying authoritative knowledge bodies.
- Verification Requests reuse this delivery path. Background requests appear in a distinct Review Inbox section and contribute only aggregate counts, reason categories, oldest age, and approaching-expiration counts to the weekly non-empty digest; they do not produce per-request notifications.
- A manual command or Memory Skill operation that directly creates a Verification Request immediately returns `waiting_verification`, the request identity, a bounded evidence gap, and candidate state. The inline operation result is not a notification and does not imply promotion.
- Source memories are edited directly in Obsidian. Confirm, adopt, disambiguate, archive, and snooze operations are also available through the canonical command surface and Memory Skill; the generated Inbox does not implement a second governance engine.
- If native notification delivery fails, permission is denied, or no acknowledgment or review activity is observed under the configured policy, the next eligible Agent Session may display one bounded SessionStart fallback notice. It is operational status, not Memory Injection, and is not repeated on every turn.
- Reminder delivery is a recoverable Reminder Obligation in the Governance Ledger. Attempted, delivered, acknowledged, snoozed, failed, and fallback states remain distinguishable; missed reminders reconcile after sleep, shutdown, or worker failure.
- A Review Suggestion relevant to the current task still produces the previously accepted bounded retrieval warning without waiting for the weekly digest.
- The first version does not send review reminders through email, Feishu, or another cloud messaging service. The core reminder obligation remains platform-neutral so additional host adapters can be added later without changing Memory Vault data.

The Obsidian URI capability is documented by [Obsidian Help](https://help.obsidian.md/Extending%2BObsidian/Obsidian%2BURI); macOS local notification behavior is documented by [Apple User Notifications](https://developer.apple.com/documentation/usernotifications).

See [ADR-0019](./docs/adr/0019-deliver-human-review-reminders-through-macos-and-obsidian.md) for the accepted reminder channels and fallback behavior and [ADR-0028](./docs/adr/0028-use-a-memstore-native-notifier-and-obsidian-review-surface.md) for notifier ownership and Verification Request presentation.

## Runtime interaction

- Ordinary capture and governance is zero-blocking and requires no per-candidate approval.
- Memory maintenance does not interrupt an active Coding Agent conversation.
- MemStore requests human judgment only when an unresolved, material conflict affects the correctness of the current task, or when the user explicitly opens a review surface.
- A conflict returned by a user-initiated remember command is part of that explicit interaction and may request one bounded resolution. It does not turn background capture or governance into an approval inbox.
- Low-frequency governance summaries and Human Memory Review Digests are observational and optional, not approval queues. Ignoring or snoozing them does not block foreground capture, retrieval, or ordinary governance.

See [ADR-0004](./docs/adr/0004-keep-runtime-governance-non-blocking.md) for the accepted non-blocking interaction model.

## Knowledge scopes

- Durable knowledge is classified as Project Memory or Global Memory.
- Agent-derived knowledge captured inside an identifiable project defaults to Project Memory and remains limited to that project boundary.
- A session without a reliable project identity does not implicitly authorize Global Memory; extracted knowledge remains unresolved until its scope can be established.
- Global Memory is intended for stable reuse across projects and requires either an explicit Manual Memory Directive or corroborating evidence from at least two independent projects with no material conflict.
- Cross-project corroboration counts distinct `project_id` values, not directories or sessions. Multiple sessions in one Project and worktrees or clones sharing a Project Marker contribute at most one project-level source.
- Each supporting project must provide traceable evidence independently originating from that project's user input, code, command result, or external evidence. Sources that merely share the same upstream assertion do not become independent by appearing in different projects.
- Capture and candidate provenance records the relevant Injection Receipt or the bounded set of Memory identities already injected into the source context. A conclusion derived from an injected Memory is a Memory Echo and cannot increase corroboration count or confidence.
- Corroborating claims must materially agree in core statement, applicability conditions, and certainty. Keyword similarity alone is insufficient, and any material Project or Global conflict blocks automatic Global promotion.
- Each project-level source must independently satisfy the ordinary promotion conditions. Automatic cross-project promotion is limited to Normal content; Private still requires an explicit human Global directive and Secret remains prohibited.
- Where project-specific conditions differ, Luna may form only the supported intersection as a new Agent-derived Global Candidate. It cannot broaden beyond shared evidence, and the original Project Memories remain unchanged with their own identities and provenance.
- The new Global Candidate has its own identity and cross-project provenance and follows the ordinary candidate lifecycle; MemStore does not change one source Project Memory's scope in place.
- The user can manually target specific content, request Luna distillation, and explicitly authorize global scope. The scope authority comes from the user's directive rather than Luna's inference.
- Manual Global authorization does not require the two-project corroboration threshold, but it does not remove provenance, conflict handling, sensitive-data checks, or the distinction between direct human assertions and model-inferred content.
- Within a project, applicable Project Memory takes retrieval precedence over Global Memory, but does not overwrite or silently modify the Global Memory.

See [ADR-0006](./docs/adr/0006-default-to-project-scope-and-require-global-intent.md) for the accepted Project/Global scope boundary and [ADR-0022](./docs/adr/0022-require-independent-cross-project-corroboration.md) for the accepted corroboration and echo-exclusion rules.

## Project identity

### Explicit session project relocation

- A user may bind one exact Codex Session ID to a registered Project without changing its working directory or Project roots. The binding takes precedence over directory resolution for that Session's Hooks and automatic recall. It does not propagate to other Sessions or forks, and explicitly requested Global extraction remains Global.
- Background extraction resolves the current Session binding when loading queued evidence and ingesting candidates. Historical evidence keeps its original Project and cwd; candidate admission and promotion recognize the authorized Session binding without weakening evidence-integrity checks.
- An approved offline migration may relocate current project memories linked by that Session's candidates and its non-rejected/non-expired candidate records. This is an explicit exception to ordinary revision scope immutability, not permission for normal agent writes to move knowledge. Shared-source memories and target candidate collisions require separate review.
- Relocation preserves Memory IDs, portable references, authorship, body, and provenance. It creates a successor revision in the destination, removes the old current canonical path, updates candidate fingerprints, and preserves historical capture, evidence, revisions, and receipts. Previously injected conversation context is not retractable.
- Migration requires a paused/stopped Worker and a coherent DB/Vault backup. A persisted migration plan supports replay after interruption. The old active retrieval snapshot is unselected until a new snapshot is built; complete historical snapshots may supply integrity-checked, identity-matching embedding vectors but may not resume serving old-scope results.
- Session routes and migration plans are machine-local runtime state. Explicit CLI/MCP calls can provide a Session ID; without one they retain normal workspace resolution rather than infer identity from inherited environment variables.

### Directory-based identity

- When no explicit Session binding applies, an existing `.memstore-project` Project Marker is the highest-priority explicit identity for Git and non-Git directories.
- Resolution searches from the current directory toward its ancestors for the nearest marker and canonicalizes examined paths through realpath or equivalent symlink resolution. A malformed or unsupported nearest marker fails safely and prevents Project Memory injection; it does not fall through to a guessed Git, basename, or registered-root identity. Independently eligible Global Memory remains available.
- A Project Marker contains a stable `project_id`, not a path to another directory. Directories that explicitly declare the same identifier share Project Memory.
- The marker is a UTF-8 JSON object. Version 1 requires integer `schema_version: 1` and a `project_id` consisting of the `msproj_` prefix followed by a lowercase UUID v4. It must not encode a path, Git remote, username, or machine identity.
- An optional string `display_name` is presentation metadata only and never participates in identity equality or memory isolation.
- Readers ignore unknown fields. Any MemStore operation that rewrites an existing marker preserves unknown fields so later schema extensions are not silently discarded.
- Invalid JSON, missing or malformed required fields, and unsupported `schema_version` values fail safely: no Project Memory is injected under the uncertain identity, scoped capture may remain unresolved, and Global Memory remains independently available.
- MemStore never creates, edits, or deletes a Project Marker during ordinary capture, injection, Luna processing, indexing, or scheduled governance.
- A Project Marker changes only through direct user editing or an explicit project-link, unlink, or equivalent Skill operation that clearly authorizes the file write.
- Without a marker, a Git repository uses the basename of its Git top-level directory as the human-facing project key. Git common-directory identity and normalized remotes provide collision evidence so same-named worktrees or clones can share while unrelated repositories are not silently merged.
- A Git basename is normalized to Unicode NFC while preserving case. A generated stable Project identity remains in the machine-local Registry and does not cause automatic marker creation.
- Same-basename Git checkouts automatically share only when their Git common directory is identical or their normalized `origin` fetch repository identity matches. Explicitly different origins create separate identities and a collision record. Missing or inconclusive evidence does not silently merge; an explicit marker or management operation is required.
- Git remote normalization maps scp-style SSH, `ssh://`, and HTTPS forms into a comparable repository identity; lowercases the host; removes userinfo, default ports, query, fragment, trailing slash, and `.git`; and preserves generic repository-path case unless a versioned provider adapter explicitly defines case-insensitivity. Only `origin` fetch identity participates by default, so a shared `upstream` does not merge forks. Local-path and `file://` remotes use a realpath-based machine-local identity and do not claim portability.
- Without an explicit marker, a Git submodule recursively inherits the outermost resolved superproject Project rather than using its own Git metadata or remote. A nearer marker overrides inheritance and produces one bounded Session operational notice naming the selected submodule Project, inherited parent Project, and how marker removal restores inheritance.
- Without a marker, each non-Git project root receives an independent generated `project_id` in the machine-local Project Registry, even when multiple roots have the same basename.
- A non-Git current directory selects the deepest realpath-normalized registered ancestor root. If none exists, the current working directory is registered as a new root without creating a marker. Moving an unmarked root requires explicit Registry relinking; portable identity requires an explicit marker.
- Machine-local path aliases and Git fingerprints are resolver state, not Canonical Memory Data.
- Invalid or conflicting identity evidence fails safely: the Agent session continues, Global Memory remains available, capture may retain unresolved scope, and potentially unrelated Project Memory is not injected.
- The MVP Project management surface is `memstore project status [--path <path>]`, `list`, `link --path <path> --to <project-id|other-path>`, `unlink --path <path>`, `relink-root --from <old-path> --to <new-path>`, `collisions`, and `resolve-collision --path <path> --use <project-id>|--separate`.
- `status`, `list`, and `collisions` are read-only and expose the final identity, display name, resolution source, matching marker or registered root, Git evidence, inherited submodule parent, aliases, last use, and collision state as applicable.
- `link` explicitly authorizes marker creation or update after resolving its target identity. It preserves unknown marker fields and only makes paths share Project identity; it does not copy, merge, migrate, or rewrite Memory. `resolve-collision --use` uses the same explicit marker mechanism.
- `unlink` recoverably renames the marker to a timestamped disabled file, previews the resulting fallback resolution, and deletes no Memory. `resolve-collision --separate` creates a new Project identity and explicit marker so later basename evidence cannot re-merge it.
- `relink-root` updates only the machine-local Registry for a moved non-Git root after validating old-root status and new-root conflicts; it creates no marker. The first version does not expose Project Memory merge or migration.
- Every write command reports affected path, old and proposed resolution, Registry effects, and marker effects and supports `--preview`. No Project management command silently moves or rewrites existing Canonical Memory.

See [ADR-0010](./docs/adr/0010-resolve-project-identity-with-repository-evidence-or-explicit-marker.md) for the accepted Project identity and marker policy, [ADR-0021](./docs/adr/0021-use-a-versioned-json-project-marker.md) for the accepted marker schema, [ADR-0072](./docs/adr/0072-normalize-project-resolution-with-conservative-collision-handling.md) for resolver normalization and collision behavior, and [ADR-0073](./docs/adr/0073-manage-project-identity-with-explicit-recoverable-commands.md) for the MVP management surface.

## Manual memory controls

- MemStore must provide a small, convenient core command surface for explicit memory operations instead of requiring the user to edit internal queue files.
- Explicit capture uses the following canonical command forms:

  ```text
  memstore remember assert
    [--scope project|global]
    [--text <content> | --stdin | --file <path>]
    [--startup auto|always|never]
    [--preview] [--json]

  memstore remember extract
    [--scope project|global]
    --from <current-turn|current-session|turn:<id>|file:<path>|selection:<id>>
    [--startup auto|always|never]
    [--preview] [--wait [seconds]] [--json]
  ```
- `assert` requires exactly one of `--text`, `--stdin`, or `--file`. `extract` requires exactly one normalized `--from` selector. Adapter-specific turn and selection identities must be resolved to durable source evidence before the operation can complete.
- `assert` creates a Direct Human Assertion. `extract` creates Agent-derived Memory Candidates and never inherits Human-authored authority merely because the user chose its source or scope.
- Project is the default scope. Global requires an explicit user phrase or `--scope global`; the command, Skill, Luna, and current repository context cannot infer that authorization.
- An omitted `--startup` value means `auto`. The selected value is applied to the resulting Memory, or to each accepted Candidate produced by `extract`, and remains subject to the ordinary eligibility and safety gates; `always` cannot force unsafe or ineligible content into injection.
- Natural-language intent that supplies an exact statement with an explicit remember or save instruction maps to `assert`. Intent that asks to extract, distill, or summarize source material maps to `extract`. Ambiguous intent fails toward `extract` rather than accidentally granting Human-authored authority.
- `assert` may complete without an extra preview when sensitivity, scope, and Human Conflict gates permit. `extract` defaults to durable background processing and returns promptly after durable enqueue rather than waiting for Luna.
- `--wait` is available only for `extract`. With no explicit value it waits up to 120 seconds; `--wait <seconds>` supplies a positive bounded timeout. A timeout stops only the caller's wait and does not cancel, roll back, or deprioritize the durable background operation. `--preview` and `--wait` are mutually exclusive, and neither may bypass the durable pipeline or report pending work as complete.
- `--json` returns a versioned stable response envelope. A non-preview accepted command reports the traceable operation or Memory identity, resolved scope, authority, current state, and a next inspection command. Human-readable output exposes the same facts without requiring the caller to parse prose.
- The canonical externally visible operation states are `completed`, `queued`, `retrying`, `waiting_verification`, `conflict`, `quarantined`, `blocked_secret`, `dead_letter`, and `failed`. A returned state describes current durable state, not a promise that asynchronous work has finished. `failed` is reserved for non-retryable operation failure; rejected command input exits before an operation is accepted.
- `--preview` is a strict dry run. It may read and resolve Project, scope, source, configuration, existing Memory, and current content and may perform in-memory schema, sensitivity, deduplication, conflict, and sanitized-size analysis. It cannot write Outbox, SQLite lifecycle or audit state, Vault, indexes, embeddings, Review Inbox, notification state, governance cursor, usage statistics, or a Project Marker and cannot call Luna.
- Preview returns `dry_run: true`, no durable operation identity, planned authority and scope, affected objects, `would_accept`, `would_create` or `would_change`, and bounded redacted warnings. It does not persist a suspected Secret fingerprint or echo the suspected value. `--preview` and `--wait` are mutually exclusive.
- Preview does not lock inputs or promise a later result. A command rerun without `--preview` re-resolves and revalidates all current state before committing. MemStore does not persist a preview audit event; shell-history behavior remains outside its control, so long content should prefer `--stdin` or `--file`.
- The command surface must support remembering explicitly supplied content with Project scope by default, remembering explicitly supplied content with Global scope, asking Luna to extract knowledge from a targeted source under a selected scope, and changing the scope of an identifiable existing memory through a governed operation.
- Remembering user-supplied content preserves it as a Direct Human Assertion. Asking Luna to extract knowledge from a source creates Agent-derived candidates; selecting Global scope authorizes only their scope and does not grant them Human-authored authority.
- An explicit update or replace operation must identify its target. A generic remember operation cannot silently infer replacement when it detects a Human-authored conflict; its result exposes the conflict and the available keep, adopt, or disambiguate actions.
- The command surface must also list and open the current human-review backlog and support confirm, adopt, disambiguate, archive, and snooze operations without requiring manual edits to internal queue state.
- The command surface may review and apply a False-positive Secret Override to one exact detection, but cannot expose a force-store-secret operation or a global detector disable.
- A manual command enters the same durable, idempotent worker pipeline as lifecycle capture; it must not invoke Luna inside a lifecycle Hook or bypass deduplication and conflict checks.
- Accepted work returns a traceable operation or memory identity so the user can inspect its result without being forced into an approval queue.
- The Codex adapter resolves `current-turn`, `current-session`, and recorded `turn:<id>` only from MemStore-owned lifecycle identities, and resolves `file:<path>` after ordinary path and scope validation. The verified first Codex version exposes no stable native selection handle, so it does not accept `selection:<id>`; user-provided text uses `assert --stdin` or extraction from the current turn or an explicit file. A later adapter may enable `selection:<id>` only when it can mint a stable, source-bound identity. Unsupported selectors fail explicitly rather than falling back to a different source.

## Memory Skill

- MemStore provides one repository-managed capture Skill named `$memstore-remember` for explicit assertions and Luna-based extraction as Project or Global knowledge.
- The Skill defaults to Project scope and uses Global scope only when the user's invocation explicitly requests it. Luna cannot infer global authorization.
- The Skill must support explicitly supplied content and targeted extraction from the current turn, selected content, or current session.
- The Skill must preserve the authority distinction between a Direct Human Assertion and Model-derived Extraction; the invocation path cannot elevate extracted content merely because the user selected its scope.
- The Skill can open or summarize the human-review backlog and route explicit resolution actions to the same canonical command or API.
- The Skill is a thin orchestration layer over the canonical MemStore command or API. It must not duplicate Durable Outbox, Luna, validation, conflict, or Vault-write logic.
- Successful invocation reports a traceable operation or memory identity. Failure or pending processing must not be presented as completed persistence.
- The canonical Skill source belongs to MemStore Project; supported Agent installations or repository-backed links must not copy Memory Vault data into Agent configuration.
- One Skill covers both Project and Global modes to centralize trigger rules and long-term maintenance.
- The Skill maps natural-language assert and extract intent to the canonical commands above. It does not implement its own preview, wait loop, or source parser beyond adapter-safe source selection.
- When intent is ambiguous, the Skill routes to `extract`. It may pass through `--wait`, `--preview`, `--startup`, and explicit scope, but it cannot reinterpret their semantics or elevate extracted content to Human-authored authority.

See [ADR-0007](./docs/adr/0007-expose-core-memory-operations-through-a-thin-skill.md) for the accepted core-command and Skill boundary, [ADR-0016](./docs/adr/0016-distinguish-direct-human-assertions-from-model-extractions.md) for its content-authority rule, [ADR-0037](./docs/adr/0037-separate-manual-assertion-from-model-extraction.md) for the accepted command and Skill UX, [ADR-0074](./docs/adr/0074-make-preview-a-zero-mutation-dry-run.md) for preview semantics, [ADR-0075](./docs/adr/0075-finalize-explicit-remember-command-contract.md) for the canonical capture syntax, wait behavior, and result states, and [ADR-0087](./docs/adr/0087-do-not-invent-selection-identities-for-codex.md) for first-host source capabilities.

## Explicit recall interfaces

- Explicit Deep Retrieval follows a compact-search then identity-based deep-read flow. Its canonical search and body-read commands are:

  ```text
  memstore recall search <query>
    [--scope current|global|project:<id>|all-projects]
    [--limit <count>]
    [--cursor <opaque-cursor>]
    [--target-tokens <count>]
    [--json]

  memstore recall show <memory-id>
    [--revision <revision-id>]
    [--detail compact|standard|full]
    [--json]
  ```
- Search defaults to `scope: current`, which means the resolved current Project plus Global Memory. `global` searches only Global Memory; `project:<id>` searches only that exact Project and does not implicitly union Global; `all-projects` performs the accepted explicitly expanded cross-Project search.
- `--limit` defaults to 16 and has a configurable implementation maximum of 50. It limits one result page, not the Agent's retrieval chain. `--target-tokens` defaults to 4,096 rendered tokens for that page. Under page pressure, search preserves more qualifying identities by shortening bounded descriptions before dropping otherwise eligible entries.
- Search results return compact descriptions, Memory and revision identities, scope, authority, source-Project labeling, and a bounded relevance reason. An opaque keyset cursor is bound to the normalized query, resolved scope, caller authorization, ranking configuration, and index revision. Callers cannot parse or construct it. A materially changed bound state returns `cursor_stale`; the Agent restarts the search rather than treating inconsistent pages as one stable result set.
- `show` defaults to the latest eligible revision at `detail: standard`. `compact`, `standard`, and `full` select the accepted representation depth. Even `full` returns the Canonical Memory body and its essential labels rather than automatically expanding provenance or relationship graphs; those remain separate progressive reads.
- The equivalent MCP contracts are `memstore_search({ query, scope, project_id?, limit?, cursor?, target_tokens? })` and `memstore_get({ memory_id, revision?, detail? })`. Identity-bearing inputs accept either the Canonical `msmem_` UUID or the portable `M:<number>` reference. CLI and MCP inputs normalize into the same core request, apply identical authorization and eligibility rules, and return the same versioned result envelope.
- `scope` is represented structurally in MCP as `current`, `global`, `project`, or `all_projects`; `project_id` is required only for `project` and rejected for other modes. MCP defaults and per-page boundaries match the CLI.
- Evidence, relationship, and irrelevant-result reporting use:

  ```text
  memstore recall provenance <memory-id>
    [--revision <revision-id>]
    [--limit <count>] [--cursor <opaque-cursor>]
    [--target-tokens <count>] [--json]

  memstore recall related <memory-id>
    [--revision <revision-id>]
    [--direction incoming|outgoing|both]
    [--limit <count>] [--cursor <opaque-cursor>]
    [--target-tokens <count>] [--json]

  memstore recall report-irrelevant
    --receipt <receipt-id> --memory <memory-id>
    [--json]
  ```
- `provenance` returns bounded, identity-bearing source and derivation records rather than copying an entire source session into one response. `related` returns exactly one relationship hop per call; an Agent may follow returned Memory identities and continue paging without a product-level total-depth or total-token limit. Both default to 16 items and a 4,096-token page target and share the opaque-cursor and maximum-page-size rules of search.
- `related` defaults to `direction: both`. It returns typed, directed edge metadata and the adjacent Memory's compact identity representation. The first version does not expose an arbitrary relationship-type expression language; callers filter returned controlled edge types locally or continue from a selected identity.
- `report-irrelevant` records only the explicit `irrelevant` observation; it does not accept free-form reasons or a broader feedback taxonomy. The cited Retrieval Receipt must prove that the exact Memory revision was returned to that caller. Recording is idempotent by receipt and returned Memory revision, and the result reports the Bad Case identity, unique observation count, and current repair state.
- Agent integrations expose seven canonical MCP tools: `memstore_search`, `memstore_get`, `memstore_provenance`, `memstore_related`, `memstore_report_irrelevant`, `memstore_archive`, and `memstore_restore`.
- The remaining MCP contracts are `memstore_provenance({ memory_id, revision?, limit?, cursor?, target_tokens? })`, `memstore_related({ memory_id, revision?, direction?, limit?, cursor?, target_tokens? })`, `memstore_report_irrelevant({ receipt_id, memory_id })`, `memstore_archive({ memory_id, reason?, apply? })`, and `memstore_restore({ memory_id, apply? })`. Their `memory_id` inputs accept either Canonical UUIDs or portable references. Lifecycle mutations preview when `apply` is omitted or false. Recall operations retain the CLI's eligibility, pagination, and versioned-error rules; lifecycle operations share the CLI lifecycle core and authority-preserving revision rules.
- The repository-managed natural-language recall Skill is named `$memstore-recall`. Agents normally call the MCP tools directly; the Skill orchestrates complex user-requested memory research without implementing a second retrieval engine.
- Search returns compact descriptions and identities. An Agent may autonomously continue with get, provenance, related, or additional pages when it judges that accurate task execution needs more information; no per-page human approval is required.
- Default explicit scope is the resolved current Project plus Global Memory. Cross-Project explicit access remains a separately reviewed policy.
- Automatic SessionStart and UserPromptSubmit injection remains strictly limited to the resolved current Project plus Global Memory. It never expands to other Projects as a fallback.
- An Agent may autonomously issue Cross-Project Explicit Recall when the default explicit search is insufficient. It must set either an exact `project_id` or `scope: all_projects`; no per-query human confirmation is required, but the expanded scope is never implicit.
- Cross-Project results are limited to eligible Normal Memory, carry prominent source-Project and non-current-applicability labels, receive a strong Project-mismatch ranking penalty, and are returned only when they remain highly semantically relevant.
- Private Project Memory cannot be read across Projects. Secret Content, Candidates, unresolved conflicts, expired and rejected content remain excluded. Cross-Project use cannot mutate scope, raise authority, or count as Global corroboration.
- Retrieval Receipts record the expansion reason, requested Projects or all-projects mode, returned Project and Memory identities, revisions, ranking information, and rendered tokens. A later Global proposal becomes a new Candidate and follows independent-project corroboration and ordinary promotion gates.
- Explicit recall reads only eligible Durable Memory and derived indexes. It cannot expose Secret Content, Memory Candidates, unresolved conflicts, expired or rejected content, or a scope the caller is not authorized to query.
- The initial result page targets no more than 4,096 rendered tokens. A retrieval chain emits one cumulative warning when it first exceeds 8,192 rendered tokens and another update for each additional 8,192-token band, but MemStore does not impose a product-level hard token limit on explicit Agent retrieval.
- Explicit retrieval does not consume the 1,200-token SessionStart budget or the automatic context-epoch injection budget. It does consume host context, tool-response capacity, and account usage; those external limits and safety boundaries remain enforceable.
- No-hard-limit means the Agent may continue paging or reading by identity, not that the first call dumps Memory Vault. Retrieval remains progressive, observable, attributable, and local without invoking Luna.

See [ADR-0038](./docs/adr/0038-use-progressive-explicit-recall-with-warnings.md) for the accepted recall surface and budget warning, [ADR-0039](./docs/adr/0039-allow-explicit-cross-project-recall-with-scope-labels.md) for the accepted cross-Project read boundary, [ADR-0076](./docs/adr/0076-page-explicit-search-and-deepen-by-memory-identity.md) for canonical search, pagination, and body-read semantics, and [ADR-0077](./docs/adr/0077-page-provenance-and-one-hop-relationships.md) for progressive evidence, relationship, and irrelevant-result reporting. ADR-0038 supersedes only ADR-0024's 8,192-token hard limit for Explicit Deep Retrieval; ADR-0024's automatic injection budgets remain accepted.

## Installation and operational CLI

- A first macOS installation uses `./install.sh` or `memstore setup`. Setup is
  preview-first and requires `--apply` before it changes Codex configuration,
  Canonical Memory, Runtime data, managed links, or LaunchAgent state.
- Setup discovers the single unambiguous Obsidian Vault, defaults machine Runtime
  data to `~/Library/Application Support/MemStore`, supports a missing Codex
  `hooks.json`, resolves absolute Node and Codex executables, verifies repository
  and notifier artifacts, and reports actionable prerequisite failures before
  managed writes.
- Active injection is the friendly default and Shadow is explicit through
  `--mode shadow`. Active preview requires explicit Codex native-memory boolean
  baselines; apply uses the existing reversible cutover and performs no native
  memory data read, import, move, or deletion.
- Apply verifies or downloads the approved E5 artifact, applies the exact managed
  integration preview, preserves a Hook symlink by changing its real target,
  bootstraps or restarts the owned LaunchAgent, waits for the foreground socket,
  and then requests notification authorization. Notification denial is visible
  but non-fatal; missing Worker readiness is a setup failure.
- `doctor --deep` reports a warning when an installed ownership manifest exists
  but the foreground Worker socket is unavailable.
- A legacy owned Active installation may refresh its ownership and rollback
  baseline without changing current Codex config or Hook bytes only when its MCP
  binding, managed Active Hook recipes, disabled native-memory flags, and every
  unrelated owned target still match the current contract. Unknown drift blocks
  adoption.

- The first-version user-facing command families are intentionally small:

  ```text
  memstore init --vault <path> [--preview] [--json]
  memstore status [--json]
  memstore doctor [--deep] [--json]

  memstore integrate codex status [--json]
  memstore integrate codex install [--preview] [--json]
  memstore integrate codex repair [--preview] [--json]
  memstore integrate codex uninstall [--preview] [--json]

  memstore worker status [--json]
  memstore worker start|stop|restart|drain [--preview] [--json]

  memstore operation show <operation-id> [--json]
  memstore operation retry <operation-id> [--preview] [--json]

  memstore governance status [--json]
  memstore governance run daily|weekly|monthly [--preview] [--wait [seconds]] [--json]

  memstore review list [--kind <kind>] [--state <state>] [--limit <count>] [--cursor <cursor>] [--json]
  memstore review show <review-id> [--json]
  memstore review open [<review-id>] [--json]
  memstore review resolve <review-id> --action <allowed-action> [--preview] [--json]
  memstore review snooze <review-id|all> (--for <duration>|--until <timestamp>) [--preview] [--json]

  memstore portability status [--json]
  memstore portability prepare [--preview] [--json]
  memstore portability adopt --vault <path> [--preview] [--json]
  ```
- Remember, recall, Project, and future cutover commands retain their separately specified surfaces. `memstore mcp serve` and `memstore hook codex <event>` are stable integration entrypoints but are not ordinary interactive workflows.
- `init` validates the Vault, produces the two initial configuration candidates, creates only MemStore-owned Vault structure after non-preview execution, initializes Runtime Data, and reports but does not install Agent integration. It never modifies `.obsidian/`.
- `status` is a fast health summary. `doctor` verifies configuration, filesystem permissions and identities, SQLite integrity and migrations, Outbox and governance backlog, Vault consistency, index revisions, Luna and notification health, Project collisions, integration ownership, and version compatibility. `--deep` may perform bounded read-only probes but no repair.
- Codex integration installation atomically managed-merges one MemStore-owned entry for each required `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Stop`, and `SessionEnd` event, the MCP server registration, and global `$memstore-remember` and `$memstore-recall` Skill links. It does not add `PreToolUse`, does not run Luna in a Hook, and preserves every pre-existing Hook, plugin, MCP server, state entry, order, and unknown field.
- Canonical Skills live in the MemStore Project and are exposed through managed global symbolic links under `~/.agents/skills`. Installation never copies Memory Vault data into Agent configuration. Repair reconciles only MemStore-owned manifest entries. Uninstall removes only entries and links whose ownership and expected target still match; it does not delete Memory Vault, Runtime Data, unrelated configuration, or modified user-owned files.
- Integration writes use compare-and-swap against the file revision inspected by preview, atomic replacement, a timestamped recoverable backup, and post-write parse plus ownership verification. A concurrent change aborts with a fresh diff rather than overwriting it. Preview obeys ADR-0074 and does not create the backup or ownership manifest.
- `operation retry` accepts only a retryable or dead-letter operation and creates an auditable retry attempt without rewriting history. It cannot retry `blocked_secret` into acceptance or bypass Review. The first version exposes no generic operation cancel that could silently discard captured work.
- Manual governance runs create or join the same durable obligations and checkpoints as scheduled runs. Preview reads and plans without Luna or ledger mutation. Wait follows the accepted caller-only timeout behavior and never cancels the durable run.
- Review actions are validated against the Review item's type. Examples include confirm, adopt, disambiguate, archive, confirm Secret, exact false-positive approval, sanitized replacement, discard, and permitted restore. A generic action cannot be applied to an incompatible item type. `open` uses the accepted Obsidian Review Inbox path and remains read-only.
- Portability status reports whether the long-term-knowledge-only migration contract is currently satisfied. Prepare drains and pauses source ownership only on real execution; adopt validates Canonical Data, creates destination Runtime state, rebuilds local indexes, and keeps capture disabled until verification succeeds. Neither command merges Runtime databases.
- All mutating commands support strict preview where a meaningful plan exists and the stable `--json` envelope. Timestamps use RFC 3339 with an explicit offset; durations use ISO 8601; IDs are opaque; cursors are opaque and query-bound. Invalid input is rejected before durable operation acceptance.

See [ADR-0086](./docs/adr/0086-install-and-operate-memstore-through-owned-idempotent-surfaces.md) for the canonical operational command families and managed Codex integration boundary, and [ADR-0127](./docs/adr/0127-install-through-a-preview-first-friendly-setup.md) for the first-install orchestration.

## Distillation model

- The intended model for knowledge distillation is `gpt-5.6-luna` (displayed locally as GPT-5.6-Luna).
- Every MemStore-managed Luna invocation explicitly uses the default service tier and medium reasoning effort. The first version does not dynamically route Luna work across reasoning levels; an inconclusive result remains retryable, waiting, or review-due under the applicable lifecycle rather than silently escalating model depth.
- The first version does not silently fall back to another model. Adding a fallback later requires explicit configuration, separate quality validation, and a reviewed ADR.
- Network failure, model unavailability, authentication or configuration errors, rate limits, timeouts, and invalid responses leave affected operations durably pending or retryable.
- Luna failure does not disable healthy local capture, retrieval and injection of existing Durable Memory, or independently valid deterministic maintenance.
- User-facing health must distinguish distillation delay from capture failure, Vault failure, and retrieval failure.
- Timeout-, unavailable-, and rate-limit-blocked Luna work is reported as paused background work while local Capture, the published Retrieval Snapshot, SQLite integrity, and foreground recall remain healthy. It does not by itself make the overall local MemStore Doctor state degraded.
- A persistent Model Health Incident records state, reason category, incident start, last successful call, most recent failure, next retry, pending operation count, and oldest backlog age.
- A confirmed transition from healthy to degraded or unavailable produces one explicit host-visible notification, not a repeated message on every turn. Recovery produces one notification.
- One isolated Luna failure remains an operation-level retry and does not create a host notification. Model state becomes `degraded` after three consecutive failures spanning at least two minutes, or when the oldest Luna-dependent retryable work reaches 15 minutes. Either transition creates one notification.
- Authentication, invalid model, or invalid configuration failures enter `unavailable` immediately. Other retryable failures become `unavailable` after 30 continuous minutes without recovery; five consecutive schema-invalid or otherwise unusable Luna responses also enter `unavailable`. The unavailable transition creates one additional notification when it follows degraded.
- Recovery requires a successful health probe followed by successful completion of at least one real queued Luna operation. Recovery creates one notification and reports whether backlog catch-up remains.
- Retry uses configurable exponential backoff with jitter: 30 seconds, then one, two, four, eight, and 15 minutes, capped at 30 minutes. A valid provider `Retry-After` takes precedence even when longer. Authentication and configuration failures avoid high-frequency retries and wait for configuration change, explicit retry, or low-frequency probing.
- An unresolved unavailable incident may remind once after 24 hours and at most once per subsequent 24-hour window. An explicit snooze suppresses those reminders until its deadline, while persistent status remains visible. Acknowledgment, snooze, retry, or notification failure never discards queued work or clears the incident by itself.
- Manual memory commands, the Memory Skill, and status surfaces always report whether work is completed, queued, retrying, or blocked and expose the current model-health state.
- Notifications do not contain prompts, memory bodies, credentials, authorization headers, or raw provider responses. They are operational UI state, not Durable Memory or a Relevant Memory Pack.
- Dismissing a notification cannot clear the incident or discard queued work.

See [ADR-0015](./docs/adr/0015-queue-luna-work-and-surface-model-health.md) for the accepted no-fallback and model-health visibility policy, [ADR-0082](./docs/adr/0082-classify-and-retry-luna-health-incidents.md) for the initial incident, retry, reminder, and recovery defaults, and [ADR-0122](./docs/adr/0122-throttle-offline-recovery-without-degrading-local-recall.md) for offline recovery throttling and local-health interpretation.

## Agent integration direction

> The Capture Inbox, Foreground Retrieval Lane, and dirty-watermark requirements below are the approved post-Cutover reliability architecture. They remain inactive until the later Implementation Evidence and Activation Reviews. The installed runtime continues to follow ADR-0103, ADR-0112, and ADR-0093 meanwhile.

- Capture is driven primarily by available per-turn and session-lifecycle hooks.
- Hook handlers normalize only bounded Capture Events and must not run Luna distillation inline.
- Capture Events or their provenance envelopes retain the bounded Memory identities injected into the source context, or a reference to the corresponding Injection Receipt, so later governance can identify Memory Echoes without storing another transcript copy.
- Before capture is acknowledged, the host adapter atomically writes one schema-validated Capture disposition to the machine-local Capture Inbox. Waking the Worker is best-effort; Worker, SQLite, model, or network unavailability must not discard an accepted disposition.
- The Capture Inbox lives under `<runtime>/spool/capture/` and is the normal Hook ingress. Normal content stores the existing bounded sanitized event envelope. Confirmed Secret content stores only a body-free `blocked_secret` disposition, and uncertain sensitivity stores only a body-free `quarantined` disposition. A Hook reports success only after the corresponding file is durable; failure remains fail-open with a host-visible warning.
- The first reviewed Capture Inbox limits are 2,048 pending files or 512 MiB total, whichever occurs first. Status and doctor warn at 75 percent of either limit and report a critical capacity state at 90 percent. At capacity the Hook fails open visibly and never overwrites an older disposition.
- The Worker idempotently imports Capture Inbox files into the SQLite Durable Outbox and removes a file only after SQLite records the same event identity or equivalent body-free rejection. SQLite remains the processing, lifecycle, retry, batching, and governance ledger; Hook processes do not normally compete for its writer lock.
- Each Outbox record uses indexed structured columns plus a schema-versioned, validated JSON payload rather than an unconstrained object. The envelope includes stable event and deduplication identities, Agent, Project, Session and Turn identities where available, event kind and time, sensitivity state, Injection Receipt reference, lifecycle, attempt, lease, retry and error metadata, and a sanitized bounded payload.
- One payload segment is limited to a configurable initial 64 KiB. Larger eligible Prompt or assistant content uses ordered rows under one event-group identity with declared segment count, per-segment checksum, and whole-content identity. The configurable first-version retained sanitized-text ceiling is 1 MiB per Turn.
- Content beyond the Turn ceiling records `source_truncated` plus original and retained byte counts and is ineligible for lightweight promotion. A worker treats a segmented source as complete only when every declared segment and checksum is present; incomplete content takes the full validation path or waits and is never presented as intact evidence.
- The Turn ceiling does not authorize full Tool input or output capture. Tool events retain the accepted generic structured summaries, key facts, exit or result state, content fingerprints, and safe source references under independent sensitivity and bounded-payload rules.
- Existing valid emergency-spool files remain compatible Capture Inbox entries and are imported without rewrite. Invalid or checksum-mismatched files move to an owner-only quarantine directory whose status surfaces do not expose bodies. Capture Inbox counts, bytes, age, dispositions, and import failures are visible without exposing captured bodies; the Inbox is not Canonical Memory, Vault data, or a second processing ledger.
- An independent Distillation Worker consumes events idempotently, coalesces related turn or session input, invokes Luna, and advances the candidate lifecycle.
- A Batch containing only `SessionStart` and `SessionEnd` lifecycle envelopes is completed deterministically with an empty structured result and still participates in Session boundary/consolidation bookkeeping. It never invokes Luna and cannot consume retries merely to restate that lifecycle metadata contains no Memory proposition. Existing blocked lifecycle-only Batches are recovered through the same bounded deterministic rule.
- Session consolidation uses only structured Batch results. When all results would exceed the Codex process input limit, the Luna adapter partitions them under a conservative character budget, consolidates each partition, and consolidates those partial results again until one Session result remains. Every level restores the exact original evidence identities. An `input_too_large` rejection is an operation-specific capacity error, not an authentication, model, or configuration incident.
- Session consolidation is not allowed to silently erase a consolidation-protected Candidate. If neither an output Candidate nor an evidence-linked consolidation disposition represents that input, the Worker restores the original Candidate before the existing 64-item admission limit and Promotion Gate. Protection covers an admitted durable Candidate backed by an explicit user statement or by at least two distinct evidence-linked importance reasons. The fallback preserves Agent-derived authority, does not recreate content rejected during distillation, and does not protect every single-signal Candidate merely because Luna attached one importance tag.
- A missing `SessionEnd` is repaired after two hours without new Session activity by an idempotent body-free synthetic `SessionEnd`. This finalizes the closed Batch range without blocking an actively changing long task; later activity continues through the next incremental consolidation generation.
- Worker state must distinguish at least captured, processing, candidate-created, skipped, retry-wait, and dead-letter outcomes. Model timeout, worker restart, and temporarily unavailable Vault writes must be retryable without creating duplicate knowledge.
- `captured`, active or lease-expired `processing`, and `retry-wait` payloads are not deleted merely because they are old. Model, network, Worker, or Vault downtime cannot convert pending recoverable work into retention expiry. An expired processing lease returns the same event identity to idempotent claiming.
- After `candidate-created`, `completed`, `skipped`, or `duplicate` becomes terminal and every required downstream Candidate, bounded evidence, and provenance record is durable, the sanitized Outbox payload defaults to 30 calendar days. Payload removal then leaves body-free event metadata or a tombstone for a configurable 180 calendar days.
- `dead-letter` is reserved for non-transient work that automation cannot continue; temporary Luna, network, Worker, or Vault unavailability remains retryable. Dead-letter payload defaults to 90 calendar days and enters the Review Inbox. If still unresolved, its body is removed, state becomes `expired_unresolved`, and body-free metadata remains under the 180-day default. Explicit review, retry, or repair activity may restart its configured review window.
- Before any Outbox body removal, maintenance rechecks terminal state, absence of an active lease, downstream evidence and provenance durability, and expected content identity. Cleanup uses bounded batches and incremental space reclamation rather than a full SQLite VACUUM after every deletion.
- The 30-day terminal-payload, 90-day dead-letter-payload, and 180-day body-free metadata periods are configurable first-version defaults. Status, Receipt, and Review surfaces distinguish replayable payload from metadata-only history and cannot claim that removed content remains recoverable.
- `Stop` is the primary per-turn capture signal. `SessionEnd` performs only bounded flush, recovery, or worker-wakeup work and must never wait for model inference.
- Scheduled jobs may perform deeper consolidation, stale-knowledge review, relationship maintenance, and candidate re-evaluation.
- `SessionStart` background injection defaults off, controlled by machine-local `[adapters].session_start_injection` (boolean). Missing, invalid, or unreadable settings disable it. Capture remains enabled; disabled startup produces no memory selections, token charge, repeat-suppression entries, or delivered-legend marker. `UserPromptSubmit` retains relevance-ranked injection and supplies the legend on its first non-empty pack. Explicit opt-in restores the bounded Core Memory Pack rules below. Changing the switch cannot retract text already delivered to an existing conversation; MCP or Skills may provide deeper retrieval.
- In active mode, one dedicated Foreground Retrieval Lane inside the existing managed MemStore process owns the owner-only Unix-domain Foreground Retrieval Endpoint. It runs on a worker thread separate from Distillation Worker orchestration, retains one model owner and one LaunchAgent, and never invokes Luna or exposes a network listener.
- The Lane admits at most one automatic request and maintains no ordinary waiting queue. Each request carries an absolute one-second deadline. Insufficient remaining budget, an occupied lane, endpoint absence, malformed protocol data, or retrieval failure returns `busy`, `deadline_exceeded`, or `unavailable` without injected context and remains fail-open for the active Codex turn.
- Client disconnect and deadline expiry cancel the request before another retrieval stage begins. An abandoned request cannot commit a successful Injection Receipt, increase Context Epoch tokens, start optional relationship expansion, or remain queued behind background work. A non-interruptible E5 call may finish only its current bounded batch; no later stage may start.
- The Lane fixes one immutable Retrieval Snapshot at request admission. The Snapshot binds the completed index revision, configuration version, Memory content identities, eligible Project and Global rows, validated representations, lexical state, vectors, and relationship adjacency. A newly published Snapshot replaces it atomically and cannot alter an in-flight request.
- A foreground request reserves its captured event in the evaluation ledger before pack preparation. A completed foreground result prevents the asynchronous Shadow evaluator from replaying the same event, restarting its Context Epoch, or double-counting selected revisions.
- A failed foreground delivery remains fail-open for that turn and is recorded as non-delivered; asynchronous Shadow observation must not retroactively create its Receipt, consume Context Epoch tokens, or replace a newer active Session epoch.
- Memory Injection reads only completed Durable Memory and derived indexes. It must not invoke Luna or expose Memory Candidates in the foreground path.
- Capture and injection failures remain fail-open for the active Agent session, but they must be observable and must not be falsely reported as successful capture.
- The Durable Outbox is recoverable operational state, not Canonical Memory Data or a second authoritative copy of Memory Vault content.
- Exact integration adapters and event semantics are specified separately for each supported Agent.

See [ADR-0005](./docs/adr/0005-decouple-hooks-from-model-processing.md) for the accepted lifecycle-hook and model-processing boundary, [ADR-0070](./docs/adr/0070-store-versioned-segmented-events-in-a-sqlite-only-outbox.md) for the original MVP Outbox format, [ADR-0103](./docs/adr/0103-add-a-bounded-emergency-capture-spool.md) for the previous exception-only recovery path, [ADR-0071](./docs/adr/0071-retain-pending-outbox-work-and-bound-terminal-payloads.md) for Outbox retention, [ADR-0094](./docs/adr/0094-consolidate-large-sessions-hierarchically.md) for bounded Session consolidation, [ADR-0116](./docs/adr/0116-isolate-automatic-retrieval-in-a-deadline-owned-foreground-lane.md) for the accepted foreground execution seam, and [ADR-0117](./docs/adr/0117-use-a-durable-capture-inbox-as-normal-hook-ingress.md) for the accepted normal Capture ingress.

## Memory Injection preparation and retrieval

- Memory Injection data is prepared when Durable Memory changes, not generated from scratch for each foreground prompt.
- A background indexer derives searchable text, a versioned Semantic Contract, validated Injection Snippet variants, lexical and semantic indexes, bounded relationship edges, and scope and authority filters from Canonical Memory Data.
- A Semantic Contract contains at least the reusable core claim, applicability conditions, meaning-changing facts that must be preserved, original certainty, and time-sensitivity or validity metadata. Meaning-changing facts include material negations, exceptions, prerequisites, prohibitions, numeric thresholds, versions, platforms, paths, commands, and state boundaries.
- A `compact` Injection Snippet is a constrained projection of that contract rather than a prefix, extractive truncation, or unconstrained summary. It must preserve the core claim and every applicable `must_preserve` item, remain independently understandable, retain certainty, and introduce no broader scope or new claim.
- Background Luna processing may generate the `compact` candidate. Local deterministic validation enforces schema, configured token ceiling, required structured anchors, and sensitivity rules; semantic preservation that cannot be established deterministically receives an asynchronous Luna assessment. When compact-quality processing is enabled, every newly written Agent-derived Active revision with an invalid compact is queued immediately. The weekly scan reconciles missed and legacy work instead of serving as the normal discovery path for new revisions. Foreground hooks and SessionStart never generate or validate compact representations.
- The first-version configurable `compact` body ceiling is 96 rendered tokens using the target-model tokenizer when available and a conservative observable estimate otherwise. Background narrative, repeated examples, full provenance, secondary explanation, relationship detail, and revision history may be omitted because identity-based deep retrieval remains available.
- Only a successfully validated snippet bound to the current Memory content identity may be published. A Canonical Memory edit invalidates prior derived snippets immediately; failure or Luna unavailability cannot keep a stale snippet eligible for the new revision.
- A Human-authored compact override is authoritative over Luna wording but remains subject to sensitivity, schema, semantic-contract coverage, and token validation. Human authority cannot make a meaning-losing or unsafe projection eligible.
- The first version does not use mechanical body-prefix truncation or body-head-plus-tail truncation as an injection fallback. An ellipsis cannot prove that omitted middle content contains no condition, exception, negation, or other meaning-changing fact. Extractive or abstractive compact wording is eligible only when the complete rendered result passes the same Semantic Contract validation.
- If no valid `compact` exists, an eligible `critical`, `strong`, or explicit `startup: always` Memory may fall back to an `identity` representation of at most 48 rendered tokens. For UserPromptSubmit only, a `high` candidate with neither compact nor identity may instead use its validated standard representation when that representation is at most 96 rendered tokens. This short-standard fallback does not apply to `probable`, post-soft, or SessionStart packs. A `normal` Memory without one of these eligible representations is omitted from automatic injection.
- `identity` contains only the Memory identity, scope, authority, primary category, a separately validated non-assertive topic label, and an explicit notice that the body is incomplete and must be read by identity before reliance. It does not contain a mechanically truncated Canonical Memory body or present itself as an executable fact.
- The topic label is generated and validated as its own bounded derived field against the current content identity. Foreground code does not construct it from body prefixes or suffixes. If no safe current label exists, the Memory is omitted rather than represented with stale or potentially misleading text.
- During pack assembly, deterministic code tries the validated compact representation, then the eligible identity fallback, then the accepted UserPromptSubmit short-standard fallback. It records `representation_unavailable`, `budget_not_fit`, or `item_limit` separately and continues with later candidates. Public receipt inspection exposes bounded omission details, and status counts `high` UserPromptSubmit omissions caused by unavailable representations against the active index. Foreground runtime never cuts a representation to make it fit.
- SessionStart uses only a validated `compact` representation of at most 96 rendered body tokens or the accepted `identity` fallback. This applies equally to eligible `startup: always` and dynamically ranked candidates. SessionStart does not inject a `standard` representation or a full Canonical Memory body because it has no task-specific prompt to justify the additional detail.
- A `standard` Injection Snippet may use at most 192 rendered body tokens and remains subject to the same Semantic Contract, sensitivity, revision-binding, and validation requirements. A validated standard of at most 96 rendered tokens may serve as the initial representation for a `high` UserPromptSubmit result when compact and identity are unavailable. Longer standard representations remain second-phase detail upgrades. `probable` remains compact-only. Explicit identity-based retrieval may return standard or progressively deeper content under its separate budget policy.
- Representation level does not change priority, authority, evidence, relevance, or scope. A longer form cannot displace a higher-ranked item merely because it contains more text.
- Retrieval Indexes, embeddings, caches, and ranking state are machine-local and rebuildable. They are not Canonical Memory Data and do not need to migrate with Memory Vault.
- Manual Obsidian edits invalidate affected derived records through content identity or equivalent change detection. A new index revision is published atomically only after it is ready; the last complete revision remains readable after a failed rebuild.
- A per-turn Retrieval Query contains the current prompt, resolved project identity, bounded structured session signals such as recent files or symbols, explicit errors or commands, Memory identities already injected in the session, and an optional bounded recent-user-prompt window.
- The recent-user-prompt window contains at most the three most recent meaningful prompts from the same Project and Session, excludes empty and short-confirmation prompts, and uses at most 256 `o200k_base` tokens. Newest-to-oldest token allowances follow a 4:2:1 ratio and oversized entries preserve their beginning and ending around an ellipsis.
- Recent user prompts participate only in a local history-enhanced semantic query for context-dependent prompts. They cannot independently become exact metadata, direct Memory identity, structured Session-signal, applicability, or relevance-score evidence, and they are never rendered into the injected pack or duplicated into the current Receipt query. For a current prompt of at most 160 Unicode code points containing an explicit contextual reference, history-enhanced semantics may corroborate an item only when semantic similarity is at least 0.82 and the current prompt itself matches at least two indexed terms; this grants only the existing two-point very-strong-semantic score and cannot independently make an item `high`. One batched local adapter call also produces a current-prompt-only vector, which orders items within the same Relevance Band and score so older context cannot dominate final Top-N selection; non-contextual prompts use only the current prompt.
- A Retrieval Query must not include the complete conversation, assistant responses, tool input or output, or invoke Luna to create a live Session summary. Detailed Source Session content is available only through explicit deeper retrieval.
- Foreground retrieval reads local completed indexes only. It filters active Durable Memory, applies Project and Global scope rules, combines lexical and semantic recall, performs bounded relationship expansion, ranks deterministically, removes redundancy and unnecessary repetition, and assembles a Relevant Memory Pack.
- Project Memory takes precedence inside its project. Memory Candidates, rejected or expired entries, superseded entries, and unresolved conflicts do not participate in normal injection.
- Automatic retrieval first applies hard safety, lifecycle, scope, and explicit applicability filters. Secret Content, non-active lifecycle states, unresolved conflict bodies, unauthorized scopes, definitively incompatible validity/platform/version conditions, and the same already-injected Memory revision cannot compete.
- Relevance itself is graded rather than an all-or-nothing strict gate. Hybrid lexical, embedding, exact metadata, bounded structured Session signals, applicability, and one-hop relationships assign eligible candidates to `high`, `probable`, or `weak` Relevance Bands.
- `high` candidates compete normally. `probable` candidates may participate only in compact identity-addressable form that preserves the key claim and invites explicit deep retrieval when needed. `weak` candidates do not enter automatic injection but remain discoverable through explicit recall.
- The first-version configurable initial limit is at most two `probable` items per UserPromptSubmit pack, at most 96 rendered tokens per item, and at most 192 rendered tokens in total. `high` items that fit cannot be displaced by `probable`, no quota is filled artificially, and a probable-only pack labels the items as automatically retrieved candidates that may be unrelated, require applicability verification, and may be ignored.
- The value two is an internal conservative starting heuristic, not an industry standard or fixed product invariant. Shadow Mode compares `max_probable_items` values 0, 1, 2, and 3 before the Full Cutover Readiness Review and reports explicit deep-read rate, irrelevant rate, displaced high items, necessary-memory recall or task outcome, rendered tokens, and duplication.
- Shadow Mode, Luna, metrics, and governance may recommend a different value but cannot change the active value. Any adjustment requires explicit human Review.
- Automatic relevance does not require lexical and embedding retrieval to agree. A sufficiently strong embedding-only result may qualify when scope and applicability match and the similarity is specific rather than generic; a distinctive lexical or exact metadata match may also qualify independently.
- The first-version explainable relevance score assigns: direct Memory identity reference `+5`; exact file, symbol, error code, command, or entity match with no applicability conflict `+4`; very strong semantic match `+4`; strong semantic or lexical match `+2`; moderate semantic or lexical match `+1`; bounded structured Session-signal match `+1`; explicit applicability match `+1`; and a one-hop relationship from an already relevant seed `+1` at most once. Broad topic similarity contributes zero.
- A single corpus-rare exact term can independently receive the exact-match score only when its prompt spelling is a structured technical identifier: it contains a digit or an identifier delimiter such as `.`, `_`, `:`, `/`, or `-`, or at least two uppercase letters before normalization. A plain natural-language word such as `registry` can contribute to multi-term exact coverage but cannot become a strong exact anchor from rarity alone.
- The initial Relevance Bands are `high` for score 4 or greater, `probable` for score 2 or 3, and `weak` for score 1 or less. Hard safety, lifecycle, scope, and explicit incompatibility filters run before scoring and cannot be offset by points.
- For the first selected embedding adapter, normalized semantic score at least 0.82 is very strong, 0.70–0.82 is strong, 0.58–0.70 is moderate, and below 0.58 contributes no semantic points. Thresholds bind to the embedding and normalization adapter version and become invalid after a material model or normalization change.
- Foreground automatic retrieval may use only a machine-local resident embedding adapter. It cannot call Luna or a network embedding provider inside SessionStart or UserPromptSubmit. Embedding produces a retrieval signal; deterministic code still owns Relevance Band assignment and injection selection.
- The resident foreground Worker retains recent user prompts in a bounded Project-and-Session-local ring. SessionStart clears the ring, no history crosses Session identity, at most 128 recently used Session rings remain resident, and Worker restart safely falls back to current-prompt-only retrieval rather than rescanning an unbounded transcript.
- An embedding adapter version binds the model and weight identity, vector dimension, pooling, normalization, distance metric, text preprocessing, and chunking version. One completed semantic index revision cannot mix vectors produced by different adapter versions.
- The selected E5-base q8 adapter embeds at most 16 documents per model call and includes `batch16` in its adapter version. Index publication may reuse only vectors whose Memory revision, content identity, and complete adapter identity match the active index. A changed batch policy requires a replacement index because real measurements showed that batch shape can change close-result ordering; the active Shadow window records the change without restarting its elapsed-time observation.
- Durable Memory changes advance a monotonic dirty catalog watermark rather than starting one build per change. The indexer waits for a 30-second quiet period but starts after at most two minutes of continuous change. Only one build runs; changes during that build schedule at most one follow-up build for the newest watermark.
- Background embedding and publication remain low-priority bounded work and yield between batches when the Foreground Retrieval Lane is occupied or has observed pressure within the previous 250 milliseconds. A consistent build may publish even when a newer watermark exists; the follow-up build catches up without invalidating that completed revision.
- Embedding model artifacts, vectors, and indexes are machine-local rebuildable Runtime Data outside Memory Vault. Canonical Memory migration does not require copying them.
- A model change builds a complete side-by-side semantic index while the last completed compatible index continues serving. The new adapter and its calibrated thresholds require representative Chinese, English, code, path, and error-information benchmarks, Shadow comparison, and explicit human Review before atomic activation.
- Foreground model unavailability or cold-start deadline pressure may produce the accepted `lexical_only` result but cannot trigger a silent cloud fallback. The exact first-version embedding model remains an implementation benchmark decision comparing at least one lightweight and one quality-oriented candidate under recall, disk, memory, and the accepted one-second Hook deadline.
- Strong lexical match means a top-three BM25/FTS result with at least 60% effective query-term coverage or one high-distinctiveness complete phrase; moderate means a top-ten result with at least 30% coverage. Tokenization and high-distinctiveness rules are versioned with the lexical adapter.
- The retrieval implementation favors the smallest embedded architecture that satisfies measured requirements. Exact metadata uses normalized local index tables, lexical retrieval uses SQLite FTS5/BM25 over only the active retrieval revision, and semantic retrieval uses a replaceable local vector-index sidecar under Runtime Data. Retired full-history FTS state is not retained. The first version does not require Qdrant, Chroma, Elasticsearch, PostgreSQL/pgvector, or another separately operated retrieval service.
- The MVP begins with exact vector scan in a resident local worker and defers ANN implementation. If representative benchmark or production evidence shows that exact scan cannot meet the accepted one-second deadline or practical memory limits at the user's real scale, an ANN backend may be proposed at an explicit implementation Review; no speculative size threshold silently switches technology.
- Exact metadata, lexical, and semantic artifacts bind to one immutable index revision and publish atomically only when every required component succeeds. Each remains rebuildable from Canonical Memory Data and does not require backup or migration with the Vault.
- A completed subset may support an explicitly recorded degraded retrieval mode when another channel is unavailable, but it cannot be reported as full hybrid retrieval. Foreground Hooks use only in-process components or a MemStore-controlled local worker and do not connect opportunistically to an external retrieval service.
- Reciprocal Rank Fusion orders candidates within their Relevance Band. Exact metadata, Project priority, applicability, authority, evidence, redundancy, and diversity act as documented tie-breakers or pack selectors rather than silently changing the band formula.
- Every automatic score records contributing signals and adapter versions in the Injection Receipt. If Shadow Mode evidence is insufficient, the initial rules remain active; any proposed change still requires explicit human Review.
- Authority and evidence affect ordering and how a result is framed, but cannot make an otherwise unrelated candidate relevant. Recency affects only time-sensitive knowledge and does not demote stable rules merely because they are old.
- Relationship expansion cannot bootstrap from an unrelated seed. Only a `high` or `probable` seed may contribute one-hop candidates, which are independently scored and remain subject to all hard filters.
- Per-turn item, token, repetition, compact-rendering, and diversity rules bound the graded approach. Short confirmations, continuation-only prompts, already-satisfied context, and genuinely irrelevant prompts still produce an empty pack.
- Each Durable Memory may define a user-controlled `startup` policy for SessionStart participation: `always`, `auto`, or `never`; an omitted value defaults to `auto`.
- The SessionStart Core Memory Pack has a 1,200-token hard limit, including pack structure, labels, references, and warnings.
- The first-version configurable Core Memory Pack item limit is 12 across `startup: always`, dynamic compact, and identity representations. The first-version configurable identity limit is four items inside that total. MemStore does not fill either allowance artificially when fewer candidates qualify.
- The 12-item and four-identity values are conservative initial engineering defaults rather than fixed product invariants. Shadow Mode records candidates omitted by each item limit separately from token-budget omissions, but Luna, metrics, and governance cannot change active values without explicit human Review.
- `always` prioritizes an otherwise eligible Memory in the Core Memory Pack but may consume at most 50% of the total limit, or 600 tokens. At least half remains available for dynamically ranked Project and Global knowledge; unused `always` capacity may flow to those dynamic items, but not in the opposite direction.
- `always` has no separate item quota beyond the total item limit, identity limit, and its 600-token content ceiling. Project and Global Memory have no fixed item ratio.
- `always` cannot bypass lifecycle, sensitivity, scope, applicability, conflict, item-count, or token-budget rules. If eligible `always` content exceeds 600 tokens, deterministic omission and a bounded, persistent validation status make the overflow observable without repeating it on every prompt.
- The eligible `always` pool is safety-filtered and deduplicated, then uses the same effective priority tiers, current-Project one-tier promotion, lexicographic key, within-tier category rotation, and `compact`-then-`identity` representation fallback as dynamic selection. `always` does not define a separate numeric order or hidden weight in the first version.
- `always` selection stops at its 600-token ceiling or the shared total-item and identity-item limits. Each omission records its exact filter, duplicate, representation, item-limit, identity-limit, or token-limit reason in the Injection Receipt and contributes to the accepted persistent overflow status.
- The selected `always` region is assembled before the dynamic region. Dynamic candidates cannot displace selected `always` content inside its permitted ceiling, while unused `always` capacity may flow to the dynamic region as already accepted.
- `auto` delegates SessionStart participation to the reviewed ranking and diversity policy. `never` excludes the Memory from SessionStart only and does not prevent relevant per-turn retrieval or explicit lookup.
- The SessionStart dynamic area has no fixed Project-to-Global token or item quota. Eligible current-Project Memory receives an explicit ranking boost, while Global Memory competes in the same pool and may outrank weaker Project items when it has greater stable utility or authority.
- Unused dynamic capacity flows in either direction. A sparse Project pool may be filled by eligible Global Memory, and strong Project Memory may use capacity that would otherwise have gone to Global; neither scope receives reserved empty space.
- SessionStart ranking favors stable preferences, architectural or safety invariants, durable decisions, recurring engineering hazards, recovery knowledge, and toolchain rules. It applies diversity so one knowledge category cannot fill the Core Memory Pack merely through repetition.
- Eligible SessionStart candidates are assigned one of three explainable priority tiers before scope adjustment: `critical` for stable Human-authored preferences or constraints, safety or architectural invariants, and active durable decisions; `strong` for verified recurring hazards, recovery knowledge, and toolchain rules; and `normal` for other eligible long-lived knowledge.
- Current-Project scope promotes a candidate by exactly one priority tier, from `normal` to `strong` or from `strong` to `critical`, and is capped at `critical`. It does not modify authority, evidence, lifecycle, relevance, or applicability. Consequently, a Global `critical` candidate may still rank ahead of a current-Project `strong` candidate.
- Usage and explicit deep-read history may contribute only a small capped tie-break signal within a priority tier. They cannot promote a candidate to another tier, prove correctness, change authority, or let frequently repeated low-value content dominate.
- Luna may asynchronously propose bounded semantic attributes such as knowledge category, applicability conditions, time sensitivity, importance tags, and evidence references during extraction, validation, or governance. These proposals do not directly rank or select foreground injection results.
- Once accepted through the applicable validation path, semantic attributes are stored as versioned structured data. Human-authored values and explicit corrections remain authoritative; Luna cannot silently overwrite them. An unresolved or ambiguous semantic classification defaults conservatively to `normal` or remains ineligible for SessionStart rather than being guessed into a higher tier.
- SessionStart never invokes Luna for classification, reranking, or pack selection. Local deterministic code derives authority, lifecycle, scope promotion, validation state, bounded utility signals, and stable tie-breaks from accepted structured data and owns the final ordering and selection.
- SessionStart orders eligible dynamic candidates with a strict lexicographic key: effective priority tier, authority, applicability specificity, evidence state, time-sensitive freshness, capped utility, and stable Memory identity. A later component cannot compensate for a lower earlier component.
- Authority ordering is Human-authored, then explicitly human-confirmed Agent-derived, then deterministically or semantically validated Agent-derived. Applicability specificity compares only already-eligible candidates and prefers a more exact match to the resolved environment and conditions. Freshness participates only for explicitly time-sensitive knowledge. Stable Memory identity is the final deterministic tie-break.
- Current-Project scope affects only the accepted one-tier promotion and receives no second scope preference inside the lexicographic key. The ordering is not an opaque weighted sum, and any future change to key components or their precedence requires explicit human Review.
- Before dynamic SessionStart pack selection, semantic duplicates and materially overlapping renditions of the same claim are collapsed to the highest-ranked eligible representative. Diversity cannot preserve duplicate wording merely to occupy another category slot.
- Dynamic selection processes effective tiers strictly in `critical`, `strong`, then `normal` order. It does not omit a fitting higher-tier item merely to admit a different category from a lower tier.
- Within each effective tier, selection rotates deterministically across knowledge categories. The first round takes at most the highest-ranked fitting item from each represented category, the second round may take one more per category, and later rounds continue the same pattern until the token or item limit is reached. Each category's queue follows the accepted lexicographic key.
- If no other category in the current tier has a fitting candidate, one category may continue consuming available capacity; diversity does not reserve empty category slots. The separate `startup: always` area is selected under its own ceiling and is not part of dynamic-category rotation.
- The first-version controlled SessionStart category taxonomy is `safety_data_integrity`, `preference_constraint`, `architecture_contract`, `failure_recovery_hazard`, `workflow_environment_toolchain`, `applicability_limitation`, and fallback `durable_reference`.
- A Memory may retain multiple validated `category_tags` for search and governance but has exactly one `primary_category` for SessionStart rotation. It cannot consume the first-round slot of more than one category.
- An explicit Human-authored `primary_category` is authoritative. Otherwise Luna may propose tags, the applicable validation path confirms them, and deterministic code selects the first matching category in this ambiguity precedence: `safety_data_integrity`, `applicability_limitation`, `preference_constraint`, `architecture_contract`, `failure_recovery_hazard`, `workflow_environment_toolchain`, then `durable_reference`.
- Category ambiguity precedence affects rotation only. It does not change the Memory's priority tier, authority, evidence, applicability, lifecycle, or scope.
- SessionStart does not load every eligible Memory body or impose one global Top-N candidate cutoff. Completed derived state exposes indexed lifecycle, scope, priority, authority, primary category, applicability, representation readiness, and stable ordering fields needed for foreground selection.
- After resolving the current Project, local code exposes logical candidate buckets by effective priority tier and primary category. Current-Project and Global candidates compete inside the same bucket and retain the accepted absence of a fixed scope quota.
- Each bucket uses deterministic keyset pagination over the accepted lexicographic key. The first-version configurable fetch page size is 16 lightweight index rows per bucket; more pages are read only when duplicate, inapplicable, unavailable, or non-fitting candidates require them.
- Pagination stops when the pack reaches its accepted item or token limit or all relevant cursors are exhausted. There is no global candidate-count hard limit, so changing page size affects database round trips and latency but cannot change the final result for the same completed index, configuration, and budgets.
- The Injection Receipt records lightweight rows examined, bucket page counts, filtered or non-fitting candidates, and the terminal stop reason. Canonical Memory bodies are not loaded merely because their index rows were scanned.
- Each selected or omitted SessionStart candidate records its effective tier, scope promotion, material structured attributes, ranking components, and decision reason in the Injection Receipt. Changing models does not alter active ranking until a governed operation produces and validates a new structured Memory revision.
- Age alone does not demote stable knowledge. Recency is considered only for explicitly time-sensitive content through last-confirmed or validity metadata.
- The `startup` policy is portable Canonical Memory Data controlled by direct human edits or explicitly authorized manual operations. Luna, usage statistics, Injection Receipts, and scheduled governance cannot silently change an explicit value.
- An invalid `startup` value excludes that Memory from SessionStart until corrected and produces a bounded validation warning without weakening independent safety filters.
- A non-empty `UserPromptSubmit` Relevant Memory Pack targets 300–600 rendered tokens, contains at most six Injection Snippets, limits each snippet to 192 rendered tokens, and has a 1,024-token hard limit. Irrelevant, short-confirmation, continuation-only, redundant, or already-satisfied prompts receive an empty pack.
- `UserPromptSubmit` derives normalized text, token sets, term postings, and portable-reference lookup when an immutable Retrieval Snapshot is loaded. Foreground work uses separately bounded lexical, semantic, and structured-signal candidate channels, while direct Memory references and exact token matches remain independently eligible. For a context-dependent prompt, the semantic channel submits the current prompt and the current prompt plus the accepted bounded recent-user-prompt window together in one local batched adapter call; `lexical_only` degradation does not promote history-only matches. Final coverage and applicability scoring uses a bounded set of current-prompt query terms and yields between deterministic batches so the foreground deadline can be observed.
- UserPromptSubmit tokenization preserves normalized complete tokens, extracts Latin identifiers across script boundaries, and adds deterministic two-character n-grams for Han, Hiragana, and Katakana. Query and indexed Memory text use the same tokenizer; no foreground model or network call performs query segmentation.
- Lexical and applicability coverage is weighted by document frequency inside the eligible Project-plus-Global scope. Terms absent from that scope remain in the coverage denominator with a neutral minimum weight rather than being treated as rare evidence. A shared Project or product term may retrieve candidates but cannot by itself receive the full exact score, corroborate semantic similarity, or make a Memory `high`.
- Exact prompt evidence becomes a primary anchor only for a direct Memory identity, a bounded structured Session signal, at least two distinct matching exact terms with at least 50% weighted exact coverage, or one exact term containing at least three Unicode code points and present in at most 1% of the eligible scope with a one-document minimum. A two-character acronym such as `MR`, `PR`, or `CI` cannot be a single-term exact anchor. Applicability requires at least two matching terms with 25% weighted coverage, or one such rare term with 15% weighted coverage. These deterministic values require explicit human Review to change.
- The six-item UserPromptSubmit limit is a ceiling rather than a fill target. Every selected item independently reaches `high` or `probable`; unused positions remain empty. One-hop relationship evidence may improve order inside an independently reached Relevance Band but cannot promote an item into a higher band.
- UserPromptSubmit uses deterministic two-phase packing. Phase one selects breadth with validated compact representations and the accepted short-standard fallback: eligible `high` candidates first, then at most the accepted two compact `probable` candidates, up to the six-item and hard-token limits. A short standard uses at most the same 96-token body allowance as compact and follows relevance rank; longer standards cannot participate in this phase.
- Phase two may upgrade selected `high` items from compact to the validated standard representation in rank order using remaining capacity. `probable` remains compact-only. Ordinary upgrades stop at the 600-token target and cannot use the 600–1,024 range merely to add detail.
- A selected compact high item is eligible for a deterministic standard upgrade only when the Retrieval Query directly references its Memory identity, exactly matches its file, symbol, error code, command, or entity metadata, or matches a structured query-relevant condition present only in the standard representation. This longer second-phase upgrade is separate from the at-most-96-token short-standard fallback for a high item that has no compact or identity. A semantic-only high item with a compact remains compact unless the Agent later uses Explicit Deep Retrieval.
- Direct Memory identity reference may use remaining space up to the 1,024-token hard limit for its standard representation. An upgrade that does not fit leaves the compact selected and never truncates it or evicts another selected item.
- Phase selection, upgrade eligibility, representation choice, fit result, and any prevented displacement are recorded in the Injection Receipt. Foreground code does not invoke Luna to decide whether standard detail is useful.
- A context epoch begins at a new `SessionStart` and ends only when the host explicitly establishes a new context after compaction or an equivalent lifecycle transition. An adapter that cannot identify the boundary reliably must not guess that the epoch budget reset.
- Automatic Memory Injection has an 8,192-token soft target and a 12,288-token hard limit per context epoch. The actual rendered SessionStart pack counts toward both totals.
- At or above the soft target, ordinary automatic recall stops. Only previously uninjected knowledge that passes a stricter relevance gate and is Human-authored or otherwise explicitly verified and high-authority may use the remaining capacity. Nothing may bypass the hard limit.
- The first-version post-soft-target gate requires an explainable relevance score of at least five and at least one primary anchor: direct Memory identity reference; exact file, symbol, error code, command, or entity match; or very-strong semantic match combined with an explicit applicability or bounded Session-signal match. A one-hop relationship or broad topic signal cannot satisfy the primary-anchor requirement.
- Post-soft-target authority and evidence require Human-authored Memory, explicitly human-confirmed Agent-derived Memory, or verified Agent-derived Memory whose effective SessionStart tier is `critical` or `strong`. Ordinary `normal` Agent-derived Memory remains available to Explicit Deep Retrieval but cannot enter automatic post-soft injection merely by accumulating relevance points.
- Post-soft automatic injection uses compact representation only, admits at most two items per UserPromptSubmit, and still enforces the accepted once-per-Memory-revision-per-epoch rule. It cannot upgrade to standard merely because capacity remains between the soft target and hard limit.
- The score-five threshold and two-item allowance are configurable first-version defaults. Shadow Mode records qualifying, blocked, explicitly deep-read, relevant, and irrelevant outcomes and may recommend changes, but no model, metric, or governance task may change them without explicit human Review.
- The same Memory identity and revision is automatically injected at most once per context epoch. A materially new revision may compete again under all eligibility and remaining-budget rules.
- Token accounting covers the final rendered pack, including structure, labels, provenance references, and warnings. It uses the target model tokenizer when available and a conservative, observable estimate otherwise.
- Explicit deeper retrieval through MCP or `$memstore-recall` uses a 4,096-rendered-token initial-page target and cumulative warnings at each 8,192-token band, without a MemStore product-level hard token limit. It does not consume the automatic epoch budget but does consume host context and account usage, supports pagination and identity-based continuation, and cannot be used by a foreground Hook to disguise automatic retrieval.
- The injected pack is clearly labeled as historical reference data rather than current user instruction and remains under the item and token budgets above.
- The first non-empty automatic Memory Pack in each Context Epoch begins with one bounded header that identifies its retrieval role, requires applicability checks, and says to follow the host instruction hierarchy. SessionStart labels its items as automatically selected project background that is not necessarily relevant to the current task. A high-relevance UserPromptSubmit pack says that automatic retrieval may include false positives and requires unrelated items to be ignored. A probable-only pack treats every item as a candidate that must be verified or ignored and names `M:<id>` deep reading. Within the same applicable authority context, current explicit instructions and verified workspace state supersede conflicting or stale Memory.
- After that first non-empty pack is durably recorded, later non-empty packs in the same Context Epoch render only the selected items inside `<memstore-candidates>` and `</memstore-candidates>`. The tag keeps retrieved candidates visibly separate from instructions without repeating the full policy. Empty packs do not consume the one-time explanation, and a new Context Epoch restores it.
- Each rendered item exposes only its portable `M:<number>` reference, `S:P` current-Project or `S:G` Global scope, Human-authored or Agent-derived authority, compact, standard, or identity representation kind, and body. Canonical Memory and Project UUIDs remain internal and are not rendered in automatic packs. Time-sensitive items additionally expose only the applicable `valid_as_of` or `valid_until` metadata. Stable items do not repeat meaningless timestamps.
- Effective priority tier, primary category, score components, evidence state, `startup: always` participation, and omission details remain in the Injection Receipt rather than consuming Agent context. `startup: always` is not rendered as an instruction-authority upgrade.
- Human-authored and Agent-derived items are visibly distinguishable. An identity-only item explicitly states that its body is incomplete and names the canonical identity-based deep-read operation before reliance.
- The first non-empty pack defines compact field abbreviations once per Context Epoch rather than repeating prose for every item or turn. The existing versioned Context Epoch legend state records delivery only with a non-empty committed Receipt. Pack structure, compact boundary tags, and all visible metadata remain part of rendered-token accounting.
- Retrieval timeout, an unavailable index, or an in-progress rebuild fails open without blocking the active Agent turn.
- The configurable warm-path latency SLO remains p95 at or below 300 milliseconds for both SessionStart and UserPromptSubmit. The foreground retrieval client waits at most 1,000 milliseconds before failing open, measured from its local socket request through retrieval, filtering, packing, Receipt persistence, serialization, and response. The Codex SessionStart and UserPromptSubmit command Hooks use a two-second host timeout so Capture and fail-open handling have headroom outside that retrieval wait.
- Client-visible latency, queue delay, computation, Receipt commit, cancellation, and work observed after the deadline are recorded separately. A server-side computation that finishes after its client has failed open is not reported as delivered injection latency.
- A successful foreground result requires a bounded Receipt and Context Epoch transaction to commit before response. That transaction uses a 50-millisecond maximum SQLite busy wait. Failure returns no context and does not alter the Context Epoch; it cannot wait through the remaining one-second budget or continue after disconnect.
- SessionStart creates its new Context Epoch in the same final transaction as its Receipt and foreground reservation completion. The lane reserves at least 100 milliseconds before opening or committing that transaction and does not reclassify an already committed result through a later deadline checkpoint.
- Foreground retrieval stops starting new candidate pages, relationship expansion, or other optional work at 450 milliseconds, reserving the remaining deadline for completion of already-started deterministic safety checks, final packing, Receipt recording, and response serialization.
- A valid cached Core Memory Pack must be bound to the resolved Project identity, completed index revision, active configuration version, and current Memory content identities. SessionStart cannot inject a stale cache merely to meet the deadline.
- A lexical-only UserPromptSubmit result may return when exact metadata and lexical retrieval, every hard eligibility filter, final deterministic packing, and Receipt recording finish within the deadline; its Retrieval Receipt records `lexical_only` and the missing semantic stage. No incomplete or partially safety-checked pack may return.
- If a valid final pack cannot be returned by the deadline, the adapter returns an empty pack and the active Agent turn continues. Automatic timeout detail stays in Receipts and aggregated health state rather than repeating in every prompt; persistent abnormality uses the accepted health-notification path.
- Foreground Doctor and Status share a current-health evaluator separate from retained audit totals. A 15-minute window detects sustained deadline, failed, unavailable, busy, and post-deadline-work outcomes (three failures, or at least twenty logical requests with a failure rate of at least two percent). Client/worker observations of the same event count once, conservatively preserving failure. Overflow failure summaries also remain visible to the evaluator.
- Foreground recovery requires ten minutes without a new failure and at least five completed logical requests after the last failure. Empty short-circuits and cancellation do not prove full-path recovery. Without sufficient subsequent traffic, old faults become `awaiting_verification`, not falsely healthy and not permanently degraded. No LLM health probes or periodic synthetic capture events are introduced.
- Doctor distinguishes `healthy`, `observing`, `degraded`, and `error`: informational recovery/synchronization states produce `observing`; current sustained faults produce `degraded`; integrity errors still dominate. Foreground and index checks expose recovery conditions and relevant evaluation deadlines. Historical records are never cleared to change health.
- Index scheduling and health share the same five-minute build/retry/backlog-coalescing wait calculation. Recovery coalescing remains bounded to thirty minutes from the outstanding dirty interval; one sixty-second scheduling grace is allowed. Unpublished changes beyond the applicable deadline are a warning, including during recovery, and successful publication automatically clears it. Waiting deadlines do not slide forward merely because Doctor was rerun. All Doctor age comparisons use one observation timestamp.
- During offline catch-up, unhealthy Luna state, at least 32 active Luna operations, or at least 128 pending Capture Events activates recovery coalescing. A compatible retrieval index rebuild waits for 32 dirty generations or 30 minutes of staleness, always yields to foreground pressure, and returns to the normal 30-second quiet/two-minute maximum policy after backlog drain. Foreground activity suppresses new background write-heavy work for five seconds.
- Explicit MCP or Skill retrieval is outside this automatic one-second deadline. MemStore records p50, p95, p99, deadline failures, lexical-only fallbacks, and recall lost to deadline pressure but cannot change active latency values without explicit human Review.
- Each retrieval attempt records an Injection Receipt with query identity, index revision, selected Memory identities and revisions, rendered token count, context-epoch automatic total, budget tier, omissions and reason, and latency. Background analysis may use receipts to improve ranking or propose governance work, but usage cannot silently change Human-authored Memory authority, delete knowledge, or change configured budgets.
- Detailed Injection Receipts and item-level ranking decisions default to a configurable 30-calendar-day retention period. Receipts referenced by explicit irrelevant observations remain protected for Bad Case diagnosis and repair. Before eligible details are deleted, the Worker adds body-free daily counts, token totals, selected and omitted item counts, and latency totals to bounded summaries. It deletes at most 1,000 Receipts per transaction, checks every six hours, catches up at 30-second intervals after downtime, yields to recent foreground retrieval pressure, retries failures visibly, and never invokes a model for cleanup. Freed SQLite pages are reused; full physical compaction is never automatic.
- Quota pressure does not silently reduce injection budgets. Crossing 70% of an available host usage window produces one bounded advisory; crossing 85% produces one bounded urgent advisory. The notices contain no Memory bodies and do not change authority, ranking, or budgets. Any automatic quota-based degradation requires a separate explicit user decision.
- Shadow Mode evaluates the accepted defaults against at least 4,096, 8,192, 12,288, and 16,384-token candidate epoch ceilings and `max_probable_items` values 0, 1, 2, and 3. It reports recall quality, irrelevant injection, high-authority truncation or displacement, probable deep-read rate, explicit follow-up retrieval, rendered tokens, duplication, cache and credit impact, and task outcomes before the Full Cutover Readiness Review.

## Codex native-memory cutover

- MemStore is the target long-term system of record, distillation, retrieval, and injection path for Codex. Long-term coexistence with Codex native Memories is not supported.
- Shadow Mode keeps native generation and injection active while MemStore captures, indexes, and evaluates retrieval without injecting foreground context.
- After Shadow Mode passes the reviewed acceptance gate, one Full Cutover disables both native generation and native `use_memories` while enabling MemStore injection. There is no intermediate Controlled Cutover or dual-generation production phase.
- The single cutover requires explicit user approval and fresh evidence for capture completeness, retrieval relevance, injection latency, fail-open behavior, worker and Vault recovery, duplicate suppression, and rollback readiness.
- Shadow Mode runs for at least seven consecutive calendar days before a Full Cutover Readiness Review. It does not impose advance quotas for Session count, retrieval opportunities, non-empty packs, or manually sampled items. The report states actual coverage and confidence rather than presenting a small sample as statistically conclusive.
- During Shadow Mode, MemStore continuously records actual Sessions, retrieval opportunities, non-empty packs, selected candidates, admitted Candidate tiers, bounded considered-rejection summaries, consolidation actions, explicit deep reads, irrelevant observations, latency, failures, and recovery evidence. Considered-rejection counts cover only memory-shaped clauses the production model explicitly considered; they are not recall evidence and do not claim complete input coverage.
- Before Full Cutover, at least one Knowledge Verification Run samples from Source Sessions without using emitted Candidates as its sampling frame. The reviewer records `matched_durable`, `missed_durable`, `correct_omission`, or `ambiguous` for each evidence group. Recall uses only matched and missed eligible durable groups: reusable, evidence-supported, in-scope knowledge that is not a pure source echo. A model may propose the review, but the final cutover evidence is Human-confirmed. The Readiness Report states the actual sample coverage and does not present a small review as statistically conclusive.
- An official Shadow window is observational rather than identity-gated after it starts. Candidate, installation, managed configuration, Hook, executable-program, and retrieval-profile changes appear in `observedChanges` for Review, but they do not invalidate, restart, shorten, or block the window from reaching Gate 6 eligibility. The only persisted lifecycle states are `active` and `completed`.
- Ordinary relevance quality, irrelevant rate, automatic recall, and sampling thresholds are not frozen before real Shadow data exists. If data is sparse, Review may inspect all available cases; if it is abundant, sampling is stratified across Project, scope, authority, Relevance Band, and anomaly type. Configuration comparisons inform the reviewed choice but need not produce formal statistical significance.
- Safety and correctness remain fixed zero-tolerance gates regardless of sample volume: no Secret body leakage; unauthorized, wrong-Project, cross-Project Private, Candidate, unresolved-conflict, expired, or rejected automatic injection; silent loss of an acknowledged event; duplicate Canonical or governance effects from replay; or foreground Hook behavior that blocks an Agent Turn instead of failing open.
- The accepted p95 300-millisecond SLO and one-second fail-open deadline remain observed product targets without a predeclared minimum request count. Required crash, sleep, network, Luna, Vault-write, and duplicate-delivery recovery exercises and native-configuration rollback rehearsal may be executed during the seven-day window rather than waiting for natural incidents.
- Full Cutover additionally requires the accepted archive-body purge milestone and its isolated destructive-path evidence. Recording purge obligations in the Engineering MVP is not sufficient evidence that the lifecycle can complete.
- Full Cutover also requires the complete foreground `$memstore-repair` workflow and fresh end-to-end Bad Case evidence. Merely collecting irrelevant observations and diagnostic bundles is not sufficient once MemStore becomes the sole memory path.
- MemStore must not change Codex memory configuration automatically when a development milestone is reached.
- Existing native-memory data is preserved and is not deleted, moved, imported, or treated as Durable Memory. The first version implements and executes no Codex native-memory import during Shadow, cutover, or ordinary operation.
- Before cutover, MemStore records a body-free inventory of the native-memory configuration and storage needed for rollback, including resolved locations, counts, relevant configuration values, and integrity metadata. It does not copy native Memory bodies into the Readiness Report, Runtime Data, or Memory Vault.
- Older knowledge that exists only in native Memory and does not reappear during Shadow is intentionally unavailable to MemStore recall after cutover. This accepted gap does not authorize implicit coexistence or low-provenance bulk import.
- A future import, if ever justified, is a new explicitly reviewed feature. Imported entries begin as provenance-labeled Agent-derived Candidates and must independently pass sensitivity, scope, deduplication, conflict, applicability, and promotion gates; they cannot overwrite Durable Memory or inherit Human-authored authority.
- Rollback restores the previously verified native-memory settings and exact pre-Cutover Hook document without discarding MemStore data or modifying the preserved native-memory store. Codex-owned `hooks.state.*.trusted_hash` value changes are preserved and excluded from configuration-drift comparison; changes to `enabled`, Hook-state membership, or any other configuration still abort automatic rollback.
- Passing every current gate never triggers an automatic configuration change. The Readiness Report exposes coverage, quality observations, safety checks, performance, recovery exercises, Bad Cases, unresolved risks, and the exact proposed configuration diff; Full Cutover still requires one explicit user approval.

See [ADR-0060](./docs/adr/0060-cut-over-directly-from-shadow-to-memstore-only.md) for the accepted direct cutover and final ownership decision, [ADR-0078](./docs/adr/0078-review-adaptive-shadow-evidence-after-seven-days.md) for the accepted observation window and adaptive Readiness Review, [ADR-0080](./docs/adr/0080-do-not-import-codex-native-memory.md) for the accepted no-import boundary, and [ADR-0115](./docs/adr/0115-preserve-codex-hook-trust-during-cutover-rollback.md) for rollback handling of host-owned trust state. ## Verified Codex constraints

Verified against the locally installed Codex CLI `0.146.0` and the refreshed Codex manual on 2026-08-04:

- Codex exposes `SessionStart`, `UserPromptSubmit`, `Stop`, and `SessionEnd` lifecycle events relevant to MemStore.
- `SessionStart` and `UserPromptSubmit` can add developer context, so both are viable Memory Injection points.
- `Stop` exposes the last assistant message and a turn identifier, making it a viable fast per-turn capture signal.
- `SessionEnd` is advisory, may occur after the session has been closed or idle for 30 minutes, defaults to a one-second timeout, and allows at most three seconds.
- Asynchronous command hooks are not currently supported.
- A hook may receive a transcript path, but the transcript format is not a stable integration contract.
- The current machine has completed the reviewed Full Cutover: Codex native memory generation and injection are disabled and MemStore injection is active. Later live configuration or program changes still require their named Review.

## Delivery process

- Requirements and system behavior are specified before implementation.
- Deferred implementation selections remain explicit; they are not silently frozen into the design.
- The user must review the completed requirements Spec before implementation begins.
- MemStore uses six explicit SDD Review Gates. Approval at one Gate authorizes only the next named phase and never implicitly authorizes later repository work, global installation, Shadow activation, or Full Cutover.
- **Gate 1 — Spec Sign-off:** the reviewed SPEC, accepted ADR set, explicit deferrals, and consistency audit are delivered. Approval authorizes creation of the Implementation Plan only; it does not authorize program implementation or machine integration.
- **Gate 2 — Implementation Plan Review:** the plan defines source layout and module boundaries, Canonical Markdown and SQLite schemas, migrations, Hook/Worker/Luna/MCP/CLI/Skill interfaces, dependencies, phased tests, expected files and machine effects, risks, rollback, and evidence. Approval authorizes repository-local implementation through Gate 3 only.
- **Gate 3 — Core Foundation Review:** implementation evidence covers initialization, dual configuration, schema validation, Project resolution, SQLite, Durable Outbox, idempotent replay, Secret detection and body-free Quarantine, Canonical Memory read/write, program/data separation, and fault-injection tests in an isolated test Vault. Approval authorizes the remaining Engineering MVP implementation through Gate 4.
- **Gate 4 — Engineering MVP Review:** fresh evidence covers the uninstalled Codex adapter; Luna batching; Candidate lifecycle and Promotion; Canonical Markdown and manual-edit invalidation; FTS5, embedding adapter, and exact vector scan; Recall CLI and MCP; capture and recall Skills; non-injected Shadow Packs; full weekly and monthly governance; Review Inbox and notifications; Worker, doctor, recovery, and portability; and synthetic Secret, replay, network, crash, and Vault-failure tests. A preview of every global integration change is delivered. Approval authorizes repository-local Gate 5 prerequisite implementation and, when explicitly included in that approval, managed development Shadow installation; it does not start the official seven-day window or authorize Full Cutover.
- **Gate 5 — Full-Cutover-Prerequisite Review:** the archive-body purge implementation passes isolated destructive tests; `$memstore-repair` passes the synthetic irrelevant Bad Case loop; Codex configuration cutover and rollback are rehearsed; managed install, repair, and uninstall preserve unrelated Hook, MCP, Plugin, and Skill state; and one candidate configuration is frozen. Approval begins the official seven-consecutive-day Shadow window. Earlier development data may inform debugging but does not count toward that fixed window.
- **Gate 6 — Seven-day Readiness and Full Cutover Review:** the Cutover Readiness Report includes actual coverage and confidence, recall and irrelevant observations, explicit deep reads, every fixed zero-tolerance result, p50/p95/p99 and fail-open timing data, Luna/Outbox/Governance/recovery state, Bad Cases, purge and repair evidence, native-memory body-free inventory, exact proposed Codex configuration diff, rollback commands and evidence, and unresolved risks. Only an explicit approval authorizes one Full Cutover.
- After cutover, MemStore verifies new-Session and supported existing-Session behavior, Hooks, MCP, automatic injection, fail-open behavior, and rollback readiness. A critical verification failure follows the prevalidated rollback path without deleting MemStore or preserved Codex native-memory data.
- A post-cutover architectural repair uses three local Review steps without reopening the historical six delivery Gates. Architecture Review accepts the proposed Spec and ADR changes but authorizes no code. Implementation Evidence Review accepts repository-local tests and real-scale replay but authorizes no live change. Activation Review accepts the exact installed-build diff, backup, restart, rollback command, and observation plan before the running Worker changes.
- Foreground reliability activation is an atomic program update: Hook commands, native-memory flags, Memory Vault contents, Project identities, Canonical Memory, and the owner-only socket path remain unchanged. The activation may add backward-compatible Runtime schema and Capture Inbox state. A failed activation restores the previous built program and restarts the same LaunchAgent; it never rolls back knowledge written before or during the observation.
- Across every Gate, global Codex configuration, global Skills, MCP, Hooks, LaunchAgent, Shadow, and Full Cutover require the specific later authorization above. Repository implementation does not authorize commit, push, PR/MR, release, or publication. Each Review uses fresh evidence rather than relying on historical success, and short test retention is confined to isolated test Vaults.
- The first Engineering MVP targets one user on macOS with the locally installed Codex and the configured Obsidian Vault. Its core domain, storage, retrieval, and host-adapter contracts remain host-neutral, but only the Codex lifecycle adapter and macOS integration are implemented and validated in this milestone.
- The first embedding model remains an implementation benchmark gate already defined by ADR-0058, not an unresolved product requirement. At least one lightweight and one quality-oriented local candidate are compared on representative Chinese, English, code, path, and error retrieval, resource use, and the current automatic deadline; activation requires a later implementation Review.
- A Claude adapter is a later explicit milestone after the Codex path is stable. It reuses the same core and adds host-specific capture and injection behavior; it does not block Codex Shadow validation or Full Cutover.
- The MVP does not implement two lifecycle adapters in parallel merely to claim multi-Agent support. Additional adapters must prove their own event semantics, latency, fail-open behavior, and context-injection compatibility before activation.
- The Engineering MVP proves an end-to-end Shadow data loop: initialize and diagnose local state; resolve Project and Global scope; capture Codex lifecycle and bounded tool events through a Durable Outbox; process idempotent Luna batches; validate and promote Candidates; write and observe Canonical Markdown; rebuild exact, FTS5, and exact-scan semantic indexes; perform explicit recall; and calculate non-injected SessionStart and UserPromptSubmit packs with Injection Receipts.
- MVP command and Skill surfaces include `memstore remember`, `memstore recall`, `$memstore-remember`, and `$memstore-recall`. The current MCP surface includes `memstore_search`, `memstore_get`, `memstore_provenance`, `memstore_related`, `memstore_report_irrelevant`, `memstore_archive`, and `memstore_restore`; they remain thin clients of the same cores rather than separate retrieval or lifecycle implementations.
- The MVP includes complete weekly and monthly Luna governance for consolidation, relationship review, staleness and conflict analysis, and bounded governance summaries. It therefore also includes the durable Governance Ledger, idempotent scheduling, missed-run catch-up, retry, and model-health behavior required for those jobs to remain truthful across sleep, network outage, process restart, and Luna unavailability.
- Weekly Governance processes changes since its last successful cursor and a bounded affected relationship neighborhood. It consolidates duplicate or overlapping Agent-derived knowledge across Batches and Sessions, updates supported relationship proposals, checks recently stale applicability, evaluates corroborated Global Candidates, and performs only the already-authorized Agent-derived merge, supersede, or archive actions. Human-authored conflict or suspected staleness becomes a Verification Request rather than an automatic edit.
- Monthly Governance performs the complete Weekly duties when they coincide and adds a restartable paginated audit across all Active and Archived metadata and the relationship graph. It examines orphaned or broken relationships, duplicate clusters, time-sensitive confirmation debt, applicability drift, Project and Global generalization, high-value inflation, irrelevant Bad Cases, retrieval distribution, index health, Luna incident trends, and governance backlog.
- Monthly Governance may identify restore, archive, or future purge obligations and produces one bounded Monthly Governance Summary plus aggregated Review Inbox items. It cannot silently change Human-authored Memory, model or adapter, ranking threshold, scope, schedule, or safety policy.
- The historical Engineering MVP only recorded archive-body purge obligations. The reviewed purge milestone now executes the three-calendar-month policy with rechecks, managed staging, catch-up, and body-free Tombstones.
- The purge milestone is a hard prerequisite for Full Cutover even though it is outside the Engineering MVP. A sole long-term memory system cannot begin production ownership while knowingly accumulating archive lifecycle debt that it cannot execute.
- Before cutover, an isolated test Vault with short test-only retention must prove ordinary purge, restore protection, `retain_forever` and pin protection, idempotent repeat execution, crash recovery, catch-up, content-identity recheck, body-free tombstone retention, index removal, and agreement among Vault, SQLite, and derived state. Test retention cannot shorten the configured three-calendar-month default for real Archived Memory.
- Governance scheduling uses an explicit IANA timezone initialized from the system timezone and then kept stable until an authorized configuration change. The first-version defaults are Weekly Governance every Monday at 19:00 and Monthly Governance on the first Monday of each month at 19:00.
- When a Monthly occurrence coincides with the Weekly occurrence, one Monthly Run executes the complete Weekly obligations and atomically satisfies both ledger obligations rather than invoking Luna twice. A missed cadence is coalesced into one catch-up run from its last successful cursor rather than replaying every missed calendar occurrence.
- Multiple missed obligations of the same cadence remain individually auditable but point to one logical Catch-up Run. Its coverage begins immediately after the last successful cadence cursor and ends at a fixed `coverage_through` timestamp captured when the run is created; coalescing execution never drops data from an earlier missed interval.
- A large Catch-up Run may execute as multiple idempotent, checkpointed batches under one stable run identity. Individual batches may checkpoint recoverable progress, but the cadence's final successful cursor and linked obligations advance to `coverage_through` only after the complete logical run succeeds.
- An occurrence that becomes due after a Catch-up Run has fixed its upper bound does not extend the in-progress range. It creates or joins the next obligation so a continuously changing endpoint cannot starve completion.
- When an overdue Monthly Catch-up includes the complete Weekly duties and its coverage contains outstanding Weekly obligations, it may satisfy those Weekly obligations atomically after success. One bounded summary reports the covered range and number of recovered occurrences rather than emitting one notification per missed date.
- Startup catch-up waits at least ten minutes and yields to foreground Hook or capture/index backlog. Only one deep governance run executes at a time; ordinary capture and indexing take priority. A failed run does not advance its cursor and follows the accepted retry and model-health policies.
- Governance timezone, local schedule, startup delay, and concurrency are configurable through explicit management operations. Luna, metrics, and governance cannot silently change them.
- The MVP includes the MemStore-owned macOS notification helper and the Obsidian `_MemStore/Review Inbox.md` interaction for Verification Requests, Human Memory conflicts, model-health incidents, and weekly or monthly governance review items. Notifications remain body-free and non-blocking under the accepted policy.
- The historical Engineering MVP milestone did not enable automatic Memory Injection or modify Codex native-memory configuration; later reviewed Gates authorized Shadow and Full Cutover separately.
- Deferred beyond the Engineering MVP are the Claude adapter, ANN or a separately operated vector database, active application-level encryption, native-memory import, the future cross-Project migration command, and the full `$memstore-repair` foreground repair workflow. Archive-body purge is no longer deferred.
- The full `$memstore-repair` workflow is a hard Full Cutover prerequisite even though it is outside the Engineering MVP. It must load a Bad Case or aggregate with storage locations, occurrence and version data, representative samples, and related Injection Receipts; confirm or warn about the required Codex + GPT-5.6 foreground model; and supply the accepted repair objectives, constraints, and evidence expectations without background auto-application.
- Before cutover, at least one synthetic irrelevant case must prove record, aggregation, Skill diagnosis, reviewed repair proposal, Bad Case replay, and risk-tier resolution. Class A and B may resolve with the accepted self-test evidence; Class C retains its required runtime observation period and opportunity count. Without a user-started Skill, MemStore only records, aggregates, and reminds.
- Engineering MVP completion requires an explicit human Review. Full Cutover remains a later one-time reviewed action only after the deferred cutover blockers and full Shadow acceptance evidence are complete.

## Quality-first Admission and explicit retrieval adjudication

- Background Luna distillation splits mixed evidence into atomic clauses before retention classification. It returns full Candidate objects only for `long_term` and `project_phase` clauses. Memory-shaped clauses that it explicitly rejects are represented only by bounded counts and samples for `no_memory`, `session_only`, `uncertain`, and `source_echo`; unrecognized input and pure tool noise may be omitted without a count.
- New exact Candidate identities map to `insert`; an existing exact fingerprint maps to `update(alias)`. Rejection summaries never produce Candidates. Consolidation receives only durable Candidates, may deduplicate, identify a source echo, or downgrade them, and cannot upgrade or restore rejected content. Semantic duplicate, subsumption, or revision remains subject to the reviewed duplicate-evidence boundary rather than a model-only action label.
- Exact run identifiers, timestamps, backup paths, current branch state, completed-action inventories, operational probes, and exact-response checks are non-memory by default unless a separately isolated clause expresses a durable recovery contract.
- Explicit CLI or MCP search may use `gpt-5.6-terra` with low reasoning effort to reduce a bounded locally retrieved page to the minimal set necessary for the current query. It returns aliases only; code validates identity membership, restores stable IDs, and retains deterministic local ordering and cursor semantics.
- Terra never executes in the automatic SessionStart or UserPromptSubmit path. Automatic injection remains local and bounded by the one-second deadline.
- Every MemStore-launched Terra or Luna process explicitly selects the standard service tier (`service_tier="default"`). Terra additionally pins `model_reasoning_effort="low"`; neither model invocation may inherit or request Fast mode.

See [ADR-0106](./docs/adr/0106-use-terra-low-only-for-explicit-retrieval-adjudication.md) for the foreground model boundary, [ADR-0107](./docs/adr/0107-derive-admission-lifecycle-from-atomic-clauses.md) for clause-first Admission and deterministic lifecycle ownership, and [ADR-0109](./docs/adr/0109-separate-considered-rejection-telemetry-from-source-first-recall.md) for independent recall verification.
