# MemStore Dreaming 只读实验结果

日期：2026-09-10。基线：main / `dreaming-baseline-2026-09-10`。

## 结论

**有条件值得推进，但不应按当前提示词直接启用自动整理。** Luna Medium 能在明确约束下合并互补规则、保护人工记忆，并利用当前源码修正旧描述；本次也发现了临时统计清理失败、合并后检索排名下降，以及初版动作声明与实际改写不一致的问题。

本实验为先导验证，未完成原设想的每主题 10–30 条规模，也未证明全库收益。最终只有 17 条目的性选取的真实记忆，按三个 project 边界分成 8、5、4 条；分组内保留部分无关规则以观察是否过度合并。全部通过 MCP Recall search/show/provenance 获取，没有直接读取生产数据库或遍历 Vault。读取接口会产生常规 retrieval receipts，因此“只读”指不修改知识内容、生命周期、配置及生产索引，并非零运行记录。

## 实验设计与可复核产物

- 实际调用 `gpt-5.6-luna` **7 次**，全部 Medium、`service_tier=default`，未开启 fast。
- 四次初版：三个分组只提供历史记忆；另对 runtime 分组补充当前源码及 README。
- 两次修订：对 acme、runtime 明确保留动作必须原文不变、互补合并条件、compact 例外条件保留，以及源码仅验证对应结论。
- 一次清理复测：对 governance 分组额外要求将一次性统计留在来源中，不复制到长期规则正文。
- 模型只能生成 JSON 提案，禁用工具、MemStore memories、业务 skills、用户配置与规则加载；复用生产隔离调用方式，不执行生产 writer。
- 输入包含全文、检索描述、authority、scope、revision、review_due 提醒与 provenance identity；provenance identity 不是原始 transcript。本轮未重新打开原始会话核实所有事实。
- 另用本机 E5-base q8 做 22 个构造查询的离线排名诊断：20 个有目标知识的问题、2 个无关问题。查询在查看第一轮模型正文结果前固定，但源于已看到的样本，非独立盲测或真实 query-log 回放。第二轮沿用相同查询，属于开发集复测。

临时产物位于父 workspace 的 `tmp/`，均未加入 Git：

- 输入快照：`tmp/memstore-dreaming-samples-20260910.json`。
- 模型执行器：`tmp/memstore-dreaming-run-20260910.mjs`。
- 排名诊断：`tmp/memstore-dreaming-retrieval-20260910.mjs`。
- 请求、输出、usage 与校验结果：`tmp/memstore-dreaming-20260910-*-input.json`、`*-process.json`、`*-result.json`。
- 固定查询：`tmp/memstore-dreaming-20260910-queries.json`。
- 排名详情：`tmp/memstore-dreaming-20260910-retrieval-result.json`。

这些文件包含本机私有记忆，不应未经筛选提交到公共仓库。文件名中的日期固定本轮实验；后续重新执行会覆盖同名临时结果，应换前缀。

## 实际效果

| 项目 | 初版 | 修订版 |
| --- | --- | --- |
| 总条目数 | 17 → 17 | 17 → 15，减少 11.8% |
| 互补知识合并 | 无 | 两组各 2 → 1 |
| Human-authored 正文 | 原文保留 | 原文与原检索描述保留 |
| 既有 review_due | 保留 | 保留，无未经验证解除 |
| SessionStart 默认关闭 | 即使给出证据也未利用 | 根据源码补充默认关闭；旧容量数值未获验证，整条标为 review_due |
| 一次性恢复统计清理 | 未清除 | 加强要求后仍未清除 |
| action=keep 与正文一致 | acme 两项不一致 | 通过字节级检查 |

### 正向案例一：合并父仓变化后的安全规则

`sample-10` 要求父仓变化后先执行子模块安全门禁；`sample-25` 描述检查项、需要停止询问的状态和禁止操作。修订版合成一条，保留：

- acme/demo 与父仓 HEAD、分支、上游变化的适用范围。
- 执行 project-specific submodule safety checks，检查父仓及子模块提交。
- 命名开发分支、人工修改、未知脏文件须停止询问。
- 未经确认不得 checkout、detach、reset、clean 或批量更新。

来源 ID 分别保留；`sample-26` 的 review_due 没有被合入或清除。`sample-11` 的人工 MR 平台偏好独立保留。主代理对照输入未发现这次合并遗漏关键安全条件；未复查原始会话或 acme 当前仓库状态，不构成当前事实再认证。

### 正向案例二：综合前台检索约束

`sample-09` 的自动注入 1 秒 / fail-open 与 `sample-23` 的本地确定性 / 禁止云端回退合并成一条。保留了“显式 MCP/Skill 检索不适用”的例外。不过这次合并也产生下面的单条排名回退，不能只凭内容读起来完整就决定上线。

### 正向案例三：有证据才能补充默认状态

`sample-31` 只描述 SessionStart 的历史容量。修订版读取本轮提供的 `src/configuration/hook-display.ts` 和 README 片段后，补充了默认关闭与显式开启条件。它没有把源码未覆盖的 12 条、1,200 tokens 等历史数字冒充为已验证现状，而是标记待复核。

这也暴露了整条记忆粒度的限制：已验证的默认状态与未验证的容量数字放在一起，会一起退出自动检索。后续设计应考虑分别保存两类事实，或按需补充容量定义证据；不应简单放宽复核门槛。

## 暴露的问题

### 1. preserve 与 cleanup 的指令仍会相互干扰

`sample-15` 中“8 个 batches、2 个 consolidations、9 个 captures、4 个候选 waiting”是某次运行结果。两轮都保留了这些数字，第二轮甚至明确要求将运行统计从长期正文移出，模型仍以历史验证结果为由保留。

实验结论只支持“当前任务设计未可靠完成清理”，不能由一个案例断言 Luna 永远做不了。下一步宜把“提取可复用规则”和“保留来源证据”分成清晰输出，而不是继续叠加相互牵制的自然语言要求。清理失败应成为可重复回归用例。

### 2. compact 缩短可能同时丢条件和检索线索

初版 `sample-08` 的 compact 丢失“不覆盖 runtime/Vault 根目录缺失”。相关查询的目标从第一位下降到第二位。`sample-27` 虽仍提及图例，改写后相关查询从第一位下降到第三位。

修订版要求未修改的条目沿用原描述，避免无收益地重写所有 compact。只有确实合并或校正的条目才生成新表示。

### 3. 结构校验通过不等于语义合格

初版两条 acme 输出标为 keep，但正文增加了检索描述中的限制。内容有来源，动作标签却错误。初始程序检查未覆盖该项，结果中的空 violations 不能解释为“全面通过”；事后对照字节发现两项，修订版新增检查后通过。

模型生成的 claims 也不应直接当作验证证书。例如修订版 `sample-18` 的 claim 将“不表示可删除 active 表”改写成“不得删除该表”，语气强于输入的授权边界；keep 正文和 compact 没变，但说明解释字段仍可能扩大结论。

## 检索诊断结果

使用 E5-base q8 的本地向量分数，在对应 project 内排序；两边均排除 review_due。**没有复现生产 lexical/hybrid、条目相关性门禁或自动注入预算，因此下表不是线上检索准确率。** 目标按原始 source ID 标注；合并项携带两个 source ID 可以提高覆盖数，但仅凭 ID 不能证明两个事实都表达正确，须结合正文 review。

| 指标 | 原始样本 | 初版仅记忆 | 初版加源码 | 修订版 |
| --- | ---: | ---: | ---: | ---: |
| 总条目数 | 17 | 17 | 17 | 15 |
| 非 review_due 条目数 | 16 | 16 | 16 | 13 |
| 20 个查询平均目标来源覆盖 @1 | 97.5% | 87.5% | 87.5% | 90.0% |
| 20 个查询平均目标来源覆盖 @3 | 100% | 100% | 100% | 95.0% |
| 全样本 body tokens | 925 | 990 | 990 | 947 |
| 全样本 compact tokens | 1,409 | 689 | 639 | 1,306 |

文本 tokens 使用 `o200k_base` 离线计数，仅用于同口径比较，不是 Luna 计费或线上注入计数。统计包含 review_due 文本。

修订版的变化需分开解读：

- acme 安全查询：第一项从只覆盖两个目标之一，变为同时覆盖两个来源。
- “显式 MCP 深读也必须在一秒内完成吗”：目标从第一降到第二。这是真实的本次向量排名回退；目标仍在 Top-3，不能据此断言线上会漏召回。
- 容量查询：`sample-31` 因未验证旧容量被主动排除，造成 @3 少一题。其余 19 个有目标查询在修订版 Top-3 均能覆盖目标来源。
- 两个无关查询用来观察相似度，未计入上述 20 题覆盖率。纯向量排序仍会给不相关条目较高分，不能把这些候选直接当作应注入内容；也不能由此声称生产门禁失效。

修订版 compact 总量减少约 7.3%，body 总量增加约 2.4%。本次不支持“Dreaming 将大幅减少 token”的结论，也不能由 17 条样本外推全库减少比例。

## 调用成本与执行状态

7 次调用全部正常退出，没有超时、没有自动重试，耗时范围约 **32.5–51.5 秒/次**，调用耗时合计 277.2 秒；部分调用并行，合计不等于总墙钟时间。事件中存在 Code Mode host 被禁用的提示，这是本实验明确禁用工具后的能力不可用提示；未导致模型任务失败，也未为消除提示重新启用工具。

| Codex 返回 usage 字段 | 合计 |
| --- | ---: |
| input_tokens | 89,155 |
| output_tokens | 12,746 |
| reasoning_output_tokens | 1,633 |
| cached_input_tokens | 0 |

按接口原字段分别记录，不将 reasoning 再加到 output 推导计费总额。没有查询官方单价或估算订阅费用；也未计入抽样时生产 Recall 可能触发的检索裁判消耗，因此这不是本轮所有相关系统调用的总账。

输入包括标准 Codex 执行上下文、实验规则、schema、记忆和 provenance/receipt 元信息。正式设计可以进一步去掉模型无用的 receipt 字段、去重来源身份，但本轮没有实测精简后的成本。当前配置已禁用业务技能和模型工具，7 次模型输出事件未发现工具执行。

## 推进建议

建议进入一个范围更窄的设计 review：**同触发条件、同操作目标的互补规则合并 + 明确源码证据支持的定向修订**。沿用现有治理、准入和 canonical 写入，不做自主扫描全库并随意重写的 Dreaming。

正式自动落地前需补齐：

1. 程序判定 keep/rewrite/merge，并校验来源与 scope；不要信任模型自行声明的动作。
2. 未改条目保留原检索表示；新合并项通过条件保留检查和生产检索回放。若排名退步，保持独立条目或为同一正文保留多个可检索视角，具体策略还需测试。
3. 将临时运行统计清理作为独立失败用例解决，不宣称现有提示词已经覆盖。
4. 原始证据缺失时，不做当前事实再认证；源码只确认部分结论时，避免把已验证与待验证事实绑定成一个整体。
5. 扩展到未见过的主题和真实查询，并验证生产写入中断恢复后，才讨论自动启用。本轮没有完成这些验证。

本轮未修改正式记忆、归档状态、准入策略、运行配置或生产代码；未 commit/push。使用 `memstore-recall` 获取带身份的样本，使用 `doc-write-to-human` 整理结果与限制。实现仍需用户批准。
