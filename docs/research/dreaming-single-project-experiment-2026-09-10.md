# 单 Project Dreaming 实验

日期：2026-09-10。代码基线：`dreaming-baseline-2026-09-10`，main。

## 结论

**同 project 的高重复主题确有整理空间，但不能仅凭 project 隔离就安全地做大批合并。** 本轮 21 条整组运行两次都未通过校验；进一步缩到四条纯冲突处理规则后，获得了值得进入下一步验证的合并结果。

上一轮也已按 project 隔离，没有跨仓库合并。本轮改变了样本数量、主题集中度和重复密度，不能将效果归因为“取消跨仓库”。

## 输入与方法

- 固定 acme project：`project-A`。未混入 global 或其他 project。
- 通过 `memstore-recall` 的 MCP search/show/provenance 获取 Git 同步、冲突、子模块及构建安全记忆。
- 搜索取得 22 个身份，其中 `sample-04` 的正文深读被访问边界拒绝，排除其内容；实际模型输入 **21 条**，包含 2 条 Human-authored、2 条 review_due。provenance 指向 12 个不同 Codex session 身份；本轮未重读这些原始会话。
- 21 条使用相同输入与提示词独立调用两次；两个 input SHA-256 完全相同。随后从同一快照选出两个小组：四条纯冲突规则、三条源码构建模式规则。
- 四次都用 Luna Medium、非 fast、禁用工具和业务 skills；没有 sourceEvidence，也没有当前事实再认证。
- 在看模型结果前固定 19 个构造查询：17 个有目标、2 个无关问题。按“任一预先指定的相关来源进入 Top-K”计命中，避免把多份重复知识都当成必须同时召回的目标。
- 排名使用本机 E5-base q8，只复现向量排序；排除 review_due，未运行生产 hybrid 排名、相关性门禁和注入预算。源 ID 命中不等于语义条件完整，另做正文对照检查。

## 结果

| 实验 | 输入 → 输出 | 关键发现 | 是否接受此提案 |
| --- | --- | --- | --- |
| 同 project 整组 A | 21 → 8 | 漏 sample-17、sample-05；一项 keep 改了 compact；合并正文遗漏独立限制 | 不接受 |
| 相同输入整组 B | 21 → 10 | 漏 sample-03；虚构输入外 sample-01；三项 keep 改了 compact；部分例外丢失 | 不接受 |
| 小组：纯冲突处理 | 4 → 1 | 来源齐全；保留停止、禁止编辑/继续/abort/批量解决、解释双方改动、等待批准、无冲突例外 | 作为实验候选保留，未写生产 |
| 小组：源码构建模式 | 3 → 1 | 结构检查通过，但例外的语法挂接范围可能扩大 | 不直接接受 |

两次整组运行都保留了两条人工正文，且没有把 review_due 升为已验证。问题集中于遗漏、来源身份错误和条件保真。A 的“已覆盖全部输入”总结与实际检查不符，说明不能信任模型自报成功。

小组源码构建结果的具体风险：输出将“未经授权不得提交、pin 更新或 blanket update”与“固定 pin 且未修改的子模块除外”连在一起，容易被理解为固定 pin 能豁免提交授权。输入描述本身的例外附着也不够清晰；无论问题来自输入还是综合，不能通过改写默认裁定。另外，将 specific component 例外挂到整条综合规则上，也可能比原来源的适用范围更宽。程序核对 sourceRefs 无法发现此类问题。

## 保守方案的检索复测

将通过本轮来源/结构检查和主代理正文检查的四条冲突规则合成一条，其余 17 条保持原样，构成一个 **21 → 18** 的模拟库。未实际修改任何记忆。

| 17 个有目标查询 | 原始样本 | 整组 A（拒绝） | 整组 B（拒绝） | 仅合并冲突规则 |
| --- | ---: | ---: | ---: | ---: |
| Top-1 身份命中 | 15/17 | 14/17 | 15/17 | 15/17 |
| Top-3 身份命中 | 17/17 | 16/17 | 17/17 | 17/17 |
| 总条目数（含待复核） | 21 | 8 | 10 | 18 |
| 正文 tokens | 1,247 | 701 | 753 | 1,116 |
| compact tokens | 1,642 | 676 | 563 | 1,404 |

仅合并冲突规则时，正文减少约 10.5%，compact 减少约 14.5%，本组 Top-1/Top-3 命中数未下降。文本计数为 `o200k_base` 的统一离线口径，非线上注入或计费计数。

整组 B 虽然 Top-3 全部命中，依然有虚构来源和语义遗漏，不能因此接受。两个无关查询不计入命中率；本轮未评估生产门禁的误注入率。这是目的性小样本和构造查询，不能外推整个 project 的压缩率、长期稳定性或线上准确率。

## 对方案的修正建议

1. Dreaming 默认只在同一 project 内选材，但仍需按同一触发条件、同一操作目标分组。
2. 优先处理语义高度重叠的少量规则；同属 Git、同属构建，不足以整组重写。
3. 模型只给局部变更提案，未提及的原条目由程序保留；任何未知来源 ID 都拒绝。不要将模型返回的列表当作新的完整知识库。
4. 明确例外分别约束哪一项动作；无法确定时不合并，必要时补源证据。
5. 来源完整、结构通过、语义条件保留、检索回放都通过后，才允许替换旧条目。检查需分别判定，不能互相替代。

小组冲突合并目前仅证明这一组可行，没有重新验证上一轮临时运行统计清理问题，也没有证明自动分组已经实现。当前建议是推进“project 内小主题、局部合并”的设计 review，暂不启用整库 Dreaming。
